# Push-уведомления CentyChat (iOS / Android)

Контракт между сервером и мобильными клиентами о push-уведомлениях. Источник правды — этот документ, `openapi.yaml` (`/devices/push-token`) и фикстуры `fixtures/http/devices.*`, `fixtures/push/*`. Реализация сервера — `server/src/push/`.

## 1. Принцип: через Google и Apple — только идентификаторы

Решение владельца (2026-10-02): переписка не покидает периметр компании. Поэтому в уведомлении, которое проходит через FCM (Google) или APNs (Apple), **нет текста сообщения, имени отправителя, названия канала** — только числовые id. Текст и имя приложение забирает **с нашего сервера** своим токеном, когда уведомление пришло (Android — обработчик FCM, iOS — Notification Service Extension), и само показывает уведомление.

Что всё-таки видят Google/Apple: токен устройства, момент отправки, вид (сообщение/звонок) и числовые id из §4 (id переписки, сообщения, звонящего). Частоту и время переписки скрыть нельзя — это цена уведомлений; содержимое не уходит.

Push необязателен: без учётных данных FCM/APNs сервер не шлёт ничего (одна строка в журнале при запуске), регистрация токена отвечает `push_enabled: false`, всё остальное работает как раньше — приложение узнаёт о новом при открытии (`/api/sync`).

## 2. Регистрация токена

`POST /api/devices/push-token` (с токеном сеанса):

```json
{ "platform": "ios", "token": "<hex>", "environment": "sandbox", "kind": "alert", "app_version": "1.0.0", "device_id": "ios-3F2A…" }
```

| Поле | Обязательно | Значения |
|---|---|---|
| `platform` | да | `ios` / `android` |
| `token` | да | Android — токен FCM (`[A-Za-z0-9_:.-]`, 20–4096); iOS — hex 64–200 |
| `kind` | нет (`alert`) | iOS: `alert` — токен APNs (сообщения), `voip` — токен PushKit (звонки); Android — только `alert` |
| `environment` | iOS — да; Android — нет (`production`) | `sandbox` — сборка из Xcode; `production` — TestFlight/App Store |
| `app_version` | нет | `[0-9A-Za-z._+-]{1,32}` |
| `device_id` | нет | тот же, что в `/auth/knock`; новый токен того же устройства (и вида) заменяет прежний |

Ответ `200 {"registered": true, "push_enabled": true|false}` (`http/devices.push-token-register.json`); повтор идемпотентен. Ошибка — `400 {error, code}` (`http/devices.push-token-invalid.json`): `INVALID_PLATFORM`, `INVALID_TOKEN`, `INVALID_ENVIRONMENT`, `INVALID_KIND`, `INVALID_APP_VERSION`, `INVALID_DEVICE_ID`. Предел — 30 запросов в минуту на сотрудника (вместе с удалением), `429 {code: "RATE_LIMITED"}` и `Retry-After: 60`. Токен в ответе не возвращается.

**Когда регистрировать.** После каждого входа (пароль, `knock`), при каждом запуске приложения с живым сеансом и при каждой смене токена поставщиком (`onNewToken` FCM, `didUpdate pushCredentials` PushKit, `didRegisterForRemoteNotifications`). iOS регистрирует **оба** токена: `alert` и `voip`.

**Привязка.** Токен принадлежит одному сотруднику и сеансу, которым его зарегистрировали:
- `/api/auth/logout` удаляет токены этого сеанса и (с `device_id`) этого устройства; `/api/auth/device/unbind` и отвязка устройства администратором — токены устройства;
- `/api/auth/refresh` переносит привязку на новый токен сеанса;
- смена пароля, отключение сотрудника, истёкший сеанс (`SESSION_MAX_DAYS`) — уведомления на эти токены больше не уходят, токены удаляются при следующей попытке;
- тот же токен, зарегистрированный другим сотрудником (тот же телефон, другой вход), переходит к нему (в журнал аудита — `push_token_rebound`);
- не больше 10 токенов на сотрудника: сверх — вытесняются самые давно обновлённые.

`DELETE /api/devices/push-token {"token": "…"}` → `{"removed": true}` для своего токена; чужой и несуществующий — одинаково `{"removed": false}` (`http/devices.push-token-delete.json`). При выходе из приложения отдельно звать не нужно — это делает `/auth/logout`.

## 3. Когда сервер шлёт уведомление

**Сообщение** (новое личное или в канале, через WS или REST): каждому получателю — участнику канала или собеседнику, кроме автора, — у которого **нет ни одного открытого сокета** (ни на одном устройстве) и не включено «Не беспокоить». Одно уведомление на сообщение на каждый подходящий токен (Android — любой, iOS — `alert`). Повтор отправки с тем же `client_msg_id` нового уведомления не даёт. Правки, удаления, прочтения уведомлений не дают.

**«Не беспокоить»** (`set_dnd`, режим переживает отключение сокета): уведомлений о сообщениях нет. Звонки при «Не беспокоить» сервер не пропускает вовсе — вызывающий получает `call_unavailable` («У сотрудника включено „Не беспокоить“»), как в настольном клиенте; уведомления о звонке тоже нет. Отдельного «без звука» для переписок на сервере нет.

**Звонок** (`call_offer`) сотруднику без сокета: если у него есть устройство для звонков (Android — токен FCM; iOS — токен `voip`), сервер шлёт уведомление о звонке и **не** отвечает вызывающему `call_unavailable`: вызов ждёт как обычно (до 2 минут; вызывающий сам сбрасывает по своему таймеру). Когда разбуженное устройство подключит сокет, сразу после `auth_success` (и `wake_state`) оно получает **тот же кадр `call_offer`** (`ws/call_offer.json`), что и при звонке онлайн, — и дальше обычный сигналинг (`call_answer` / `call_rejected`). Если вызов уже сброшен (`call_end` от вызывающего) или истёк — кадра не будет. Нет подходящего токена или push выключен — `call_unavailable` «Сотрудник сейчас не в сети», как раньше.

Сотрудник, у которого открыт хоть один сокет (например, настольный клиент), уведомлений не получает: событие приходит по сокету.

## 4. Полезная нагрузка

Сообщение:

```json
{ "type": "message", "conversationType": "direct", "targetId": 2, "messageId": 41 }
```

- `conversationType` — `direct` / `channel`;
- `targetId` — переписка **с точки зрения получателя**: id канала, а в личной — id собеседника (автора). Это то же значение, что клиент передаёт в `mark_read` и `GET /api/messages?conversationType=…&targetId=…`;
- `messageId` — id сообщения.

Звонок:

```json
{ "type": "call", "callerId": 2 }
```

- `callerId` — кто звонит; `callId` (строка) появится, когда в протоколе будет номер звонка, — клиент принимает его как необязательный.

Как это лежит у поставщиков (фикстуры собраны кодом сервера):

| | Android (FCM v1) | iOS (APNs) |
|---|---|---|
| Где id | `message.data` — **все значения строки** (`"targetId": "2"`) | верхний уровень payload — **числа** |
| Сообщение | data-only (без блока `notification`), `android.priority: HIGH`, `ttl: 86400s`, `collapse_key: m-<conversationType>-<targetId>` (`push/fcm.message.direct.json`, `.channel.json`) | `apns-push-type: alert`, `apns-topic: <bundle>`, `apns-priority: 10`, `apns-expiration: now+86400`, `apns-collapse-id: m-<conversationType>-<targetId>`; `aps: {alert: {body: "Новое сообщение"}, sound: "default", mutable-content: 1, thread-id: "<conversationType>-<targetId>"}` (`push/apns.message.direct.json`, `.channel.json`) |
| Звонок | `android.priority: HIGH`, `ttl: 30s`, без `collapse_key` (`push/fcm.call.json`) | PushKit: `apns-topic: <bundle>.voip`, `apns-push-type: voip`, `apns-priority: 10`, `apns-expiration: now+30`, payload без `aps` (`push/apns.call.json`) |

Схлопывание: пока устройство недоступно, поставщик держит для переписки только последнее уведомление; на iOS новое уведомление той же переписки заменяет показанное. Клиент принимает и неизвестные поля, и неизвестный `type` (игнорирует).

## 5. Поведение приложения

**На переднем плане** (сокет открыт): сервер уведомлений не шлёт — всё приходит по сокету. Если уведомление всё же пришло (сокет только что подключился), приложение его не показывает, когда сообщение уже есть в модели (`messageId`) или открыта эта переписка.

**В фоне / выгружено:**
- Android: `FirebaseMessagingService.onMessageReceived` (data-сообщение высокого приоритета будит приложение) → `GET /api/messages?conversationType=…&targetId=…&afterId=<messageId − 1>` (или `/api/sync`) своим токеном → локальное уведомление с именем и текстом, канал уведомлений «Сообщения», группировка по переписке. Нет сети/токен мёртв/сообщение удалено — общий текст «Новое сообщение» без подробностей (или ничего, если удалено). Android может понижать приоритет приложению, которое на high-priority data не показывает уведомление, — показывать всегда.
- iOS: Notification Service Extension (`mutable-content: 1`) за отведённое время (~30 с) берёт текст с сервера токеном из общей с приложением связки ключей (App Group) и подменяет `body`/`title`; не успело или нет сети — остаётся «Новое сообщение». Группировка — `thread-id`.
- Нажатие — открыть переписку (`conversationType`, `targetId`), затем обычная синхронизация.
- Значок (badge) сервер не ставит: счётчик приложение считает само (`unread_snapshot`).

**Звонок:**
- iOS (PushKit): по правилам Apple **каждое** VoIP-уведомление немедленно сообщается в CallKit (`reportNewIncomingCall`), иначе система перестаёт будить приложение. Затем — подключение сокета и ожидание `call_offer` от `callerId`; не пришёл в течение 10 с после `auth_success` — завершить звонок в CallKit как пропущенный.
- Android: высокоприоритетное FCM → полноэкранное уведомление о входящем звонке (`CallStyle`, канал «Звонки») → подключение сокета → то же правило 10 с.
- Принять/отклонить — обычные `call_answer` / `call_rejected` по сокету.

## 6. Надёжность и ограничения

- Доставка асинхронная: путь сообщения уведомления не ждёт (очередь с ограниченной параллельностью). Временные ошибки поставщика — повтор с растущей паузой (до 4 попыток), недействительный токен (FCM `UNREGISTERED`, `SENDER_ID_MISMATCH`; APNs 410, `BadDeviceToken`, `DeviceTokenNotForTopic`) — удаляется. Push — **подсказка, а не канал доставки**: уведомление может не прийти, прийти дважды или с опозданием; источник правды — `/api/sync`.
- Очередь в памяти процесса: перезапуск сервера теряет неотправленные уведомления (сообщения при этом не теряются).
- Поставщики и их адреса зашиты в код (`fcm.googleapis.com`, `oauth2.googleapis.com`, `api.push.apple.com`, `api.sandbox.push.apple.com`); настройками их не сменить.
