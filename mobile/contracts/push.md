# Push-уведомления CentyChat (iOS / Android)

Контракт между сервером и мобильными клиентами о push-уведомлениях. Источник правды — этот документ, `openapi.yaml` (`/devices/push-token`) и фикстуры `fixtures/http/devices.*`, `fixtures/push/*`. Реализация сервера — `server/src/push/`.

## 1. Принцип: через Google и Apple — только идентификаторы

Решение владельца (2026-10-02): переписка не покидает периметр компании. Поэтому в уведомлении, которое проходит через FCM (Google) или APNs (Apple), **нет текста сообщения, имени отправителя, названия канала** — только числовые id. Android забирает текст и имя **с нашего сервера** своим токеном в обработчике FCM и показывает локальное уведомление. На iOS v1 показывает общий системный текст «Новое сообщение» на экране блокировки; приложение загружает содержимое с сервера после запуска (например, когда пользователь нажимает уведомление). Notification Service Extension для получения текста до показа уведомления пока нет.

Что всё-таки видят Google/Apple: токен устройства, момент отправки, вид (сообщение/звонок) и числовые id из §4 (id переписки, сообщения, звонящего). Частоту и время переписки скрыть нельзя — это цена уведомлений; содержимое не уходит.

Push необязателен: без учётных данных FCM/APNs сервер не шлёт ничего (одна строка в журнале при запуске), регистрация токена отвечает `push_enabled: false`, всё остальное работает как раньше — приложение узнаёт о новом при открытии (`/api/sync`).

## 2. Регистрация токена

`POST /api/devices/push-token` (с токеном сеанса):

```json
{ "platform": "ios", "token": "<hex>", "environment": "sandbox", "kind": "alert", "app_version": "1.0.0", "device_id": "ios-3F2A…" }
```

| Поле | Обязательно | Значения |
|---|---|---|
| `platform` | да | `ios` / `android` |
| `token` | да | Android — токен FCM (`[A-Za-z0-9_:.-]`, 20–4096); iOS — hex 64–200 |
| `kind` | нет (`alert`) | iOS: `alert` — токен APNs (сообщения), `voip` — токен PushKit (звонки); Android — только `alert` |
| `environment` | iOS — да; Android — нет (`production`) | `sandbox` — сборка из Xcode; `production` — TestFlight/App Store |
| `app_version` | нет | `[0-9A-Za-z._+-]{1,32}` |
| `device_id` | нет | тот же, что в `/auth/knock`; новый токен того же устройства (и вида) заменяет прежний |

Ответ `200 {"registered": true, "push_enabled": true|false}` (`http/devices.push-token-register.json`); повтор идемпотентен. Ошибка — `400 {error, code}` (`http/devices.push-token-invalid.json`): `INVALID_PLATFORM`, `INVALID_TOKEN`, `INVALID_ENVIRONMENT`, `INVALID_KIND`, `INVALID_APP_VERSION`, `INVALID_DEVICE_ID`. Предел — 30 запросов в минуту на сотрудника (вместе с удалением), `429 {code: "RATE_LIMITED"}` и `Retry-After: 60`. Токен в ответе не возвращается.

**Когда регистрировать.** После каждого входа (пароль, `knock`), при каждом запуске приложения с живым сеансом и при каждой смене токена поставщиком (`onNewToken` FCM, `didRegisterForRemoteNotifications`). iOS v1 регистрирует только APNs `alert` токен. Серверный контракт также описывает `voip` для будущей интеграции PushKit; приложение пока такой токен не регистрирует.

**Привязка.** Владение строкой токена и есть доказательство устройства: сервер не проверяет, что токен выдан именно этому телефону (поставщики такой проверки не дают), поэтому регистрация требует действующего сеанса, а токен переходит к тому, кто зарегистрировал его последним. Токен принадлежит одному сотруднику и сеансу, которым его зарегистрировали:
- `/api/auth/logout` удаляет токены этого сеанса и (с `device_id`) этого устройства; `/api/auth/device/unbind` и отвязка устройства администратором — токены устройства;
- `/api/auth/refresh` переносит привязку на новый токен сеанса (и регистрация старым токеном в паузу после продления тоже привязывается к новому); выход сеансом старого формата (без `jti`) снимает токены, зарегистрированные без `jti`;
- смена пароля, отключение сотрудника, истёкший сеанс (`SESSION_MAX_DAYS`) — уведомления на эти токены больше не уходят, токены удаляются при следующей попытке;
- тот же токен, зарегистрированный другим сотрудником (тот же телефон, другой вход), переходит к нему (в журнал аудита — `push_token_rebound`);
- не больше 10 токенов на сотрудника: сверх — вытесняются самые давно обновлённые.

`DELETE /api/devices/push-token {"token": "…"}` → `{"removed": true}` для своего токена; чужой и несуществующий — одинаково `{"removed": false}` (`http/devices.push-token-delete.json`). При выходе из приложения отдельно звать не нужно — это делает `/auth/logout`.

## 3. Когда сервер шлёт уведомление

**Сообщение** (новое личное или в канале, через WS или REST) — по правилу «смотрит ли сотрудник этот чат» (`multi-device.md` §5, функция `notify-decision`, векторы `fixtures/notify/`): никому, если это автор, если включено «Не беспокоить» или если этот чат открыт на переднем плане (`viewing` на сокете `online`) **на любом** устройстве получателя; иначе — на каждое устройство с подходящим токеном (Android — любой, iOS — `alert`), у которого **нет сокета `online`** (сокета нет или он в фоне). Устройство сокета узнаётся по `device_id` из кадра `auth` — тому же, что при регистрации токена; токен без `device_id` считается отдельным устройством. Решение принимается при рассылке и заново перед каждой попыткой доставки; задание и повторы снимаются, если переписку прочитали после постановки. В очередь попадают только получатели, у которых есть кому слать push; звонкам — резерв мест сверх предела очереди и место впереди сообщений. Одно уведомление на сообщение на устройство. Повтор отправки с тем же `client_msg_id` нового уведомления не даёт. Правки, удаления, прочтения уведомлений не дают.

**«Не беспокоить»** (`set_dnd`, режим переживает отключение сокета): уведомлений о сообщениях нет. Звонки при «Не беспокоить» сервер не пропускает вовсе — вызывающий получает `call_unavailable` («У сотрудника включено „Не беспокоить“»), как в настольном клиенте; уведомления о звонке тоже нет. Отдельного «без звука» для переписок на сервере нет.

**Звонок** (`call_offer`) с push на устройство без сокета `online` — жизненный цикл (кому уходит push — правило ниже в этом разделе):

1. **Вызов.** Если у вызываемого есть **живое** устройство для звонков (Android — токен FCM; iOS — токен `voip`; сеанс, зарегистрировавший токен, ещё действует), сервер шлёт уведомление о звонке и **не** отвечает вызывающему `call_unavailable`: вызов ждёт как обычно (`pendingOffers`, до 2 минут). Живого устройства нет или push выключен — сразу `call_unavailable` «Сотрудник сейчас не в сети», как раньше. Если вызывающий сбросил вызов (`call_end` / `call_rejected`) или отключился, пока сервер проверял его сеанс и устройства вызываемого, вызов не встаёт: уведомления нет, вызываемому при входе ничего не приходит.
2. **Окно звонка — 30 с от вызова.** Срок у поставщика (`apns-expiration`, FCM `ttl`) считается от времени вызова, а не от попытки; повтор, который не успевает в окно, не планируется. Уведомление и его повторы снимаются, как только вызова больше нет (вызывающий сбросил, вызов истёк, вызываемый подключился).
3. **Не разбудили.** Если ни одно устройство не приняло уведомление (все ответы поставщика — недействительный токен, ошибка или повторы исчерпаны/не успевают в окно; очередь push переполнена и уведомление не поставлено), вызывающему приходит `call_unavailable` «Сотрудник сейчас не в сети», вызов снимается. Считается только судьба уведомлений **этого** вызова: запоздавший провал доставки прежнего вызова той же пары (сбросил и перезвонил) новый вызов не снимает.
4. **Вход вызываемого.** Сразу после `auth_success` (и `wake_state`) разбуженное устройство получает **тот же кадр `call_offer`** (`ws/call_offer.json`), что и при звонке онлайн, — дальше обычный сигналинг (`call_answer` / `call_rejected`).
5. **Вызов закончился до входа.** Если вызов через push закончился до подключения вызываемого, в течение 60 с при входе приходит `call_end {senderId: <звонивший>, senderName, reason}` (форма — `ws/call_end.no_call.json`). Поддержка этого события интерфейсом CallKit/системным экраном звонка относится к будущей интеграции PushKit/CallKit; её нет в iOS v1. Если на вызов уже ответило другое устройство сотрудника и разговор идёт, вошедшее устройство получает `call_end … reason: "answered_elsewhere"` (`ws/call_end.answered_elsewhere.json`). `reason`: `cancelled` — вызывающий сбросил; `connection_lost` — вызывающий отключился; `timeout` — вызов истёк (2 минуты без ответа); `unavailable` — устройство не разбудили (п. 3). Этот `call_end` приходит **один раз** — первому сокету вызываемого, вошедшему после конца вызова; повторный вход (сокет в фоне переподключился) его не повторяет. Поэтому второе устройство того же сотрудника, разбуженное тем же вызовом, `call_end` может не получить и гасит звонок по правилу 10 с (§5). Это сделано намеренно: повторный `call_end` от того же `senderId` пришёл бы и в новый разговор с этим собеседником и оборвал бы его.
6. **Опоздавший ответ.** `call_answer` на вызов, которого уже нет, не начинает разговор: отвечающему приходит `call_end` с `senderId` того, кому отвечали, и `reason` из п. 5 (в течение 60 с, даже если `call_end` при входе уже приходил) или `no_call`.
7. **Повторный ответ.** `call_answer` с того же сокета, когда разговор с этим собеседником уже начат (например, параллельно ответили разные интерфейсы), идемпотентен: сервер его молча игнорирует — не пересылает и **не** отвечает `call_end`. Клиенту не нужно защищаться от двойной отправки ответа с одного устройства.
8. **Одно устройство на разговор** (задача 20). Отвечает первое устройство, приславшее `call_answer`; остальные сокеты сотрудника сразу получают `call_end {senderId: <звонивший>, reason: "answered_elsewhere"}`, а их `call_answer`, `call_rejected`, `call_end` во время разговора не действуют (на `call_answer` — тот же `call_end … answered_elsewhere`). Звук идёт только между сокетом, с которого звонили, и сокетом, которым ответили; закрылся любой из них — разговор окончен (`connection_lost`), даже если у сотрудника остались другие устройства.
9. **Номер вызова.** Доставка push о звонке и её повторы привязаны к номеру вызова (`offerSeq`, внутренний счётчик сервера, растёт с каждым вызовом), а не ко времени вызова: два вызова одной пары в одну миллисекунду не путаются. В полезную нагрузку номер не входит (§4).

**Прочтение** на одном устройстве (`mark_read`, что-то действительно прочитано): тихий push `read` (§4) устройствам читателя без сокета `online` — только по переписке, о которой ему уходил push о сообщении после прошлого прочтения. Как получится: не гарантируется (особенно iOS), после перезапуска сервера не придёт.

**Кому звонок** (`multi-device.md` §5): push о звонке — каждому устройству вызываемого с живым токеном звонков (Android — FCM, iOS — PushKit `voip`), у которого **нет сокета `online`**, даже если другие его устройства на связи (компьютер простаивает — звонит по кадру, телефон в кармане — будится push). Кадр `call_offer` получают все сокеты; сокет в фоне (`away`) на устройстве, которое будит push, получает кадр без звонка (звонит push, а не оба сразу). Ни одного сокета, который звонит (на переднем плане или без push), и ни одного устройства для push — вызывающему `call_unavailable`. «Не беспокоить» и свой вызов — ни звонка, ни push. Функция `decideCallNotification` (`server/src/push/notify-decision.js`), векторы `fixtures/notify/c01`–`c10` — источник истины. Раньше этот документ говорил «push о звонке — только сотруднику без единого сокета»; сервер так не делает, верно правило выше.

## 4. Полезная нагрузка

Сообщение:

```json
{ "type": "message", "conversationType": "direct", "targetId": 2, "messageId": 41 }
```

- `conversationType` — `direct` / `channel`;
- `targetId` — переписка **с точки зрения получателя**: id канала, а в личной — id собеседника (автора). Это то же значение, что клиент передаёт в `mark_read` и `GET /api/messages?conversationType=…&targetId=…`;
- `messageId` — id сообщения.

Прочитано на другом устройстве (тихий, ничего не показывать — снять показанные уведомления переписки):

```json
{ "type": "read", "conversationType": "direct", "targetId": 2 }
```

`targetId` — как у сообщения (с точки зрения получателя). FCM: data-only, `android.priority: NORMAL`, `ttl: 86400s`, `collapse_key: r-<conversationType>-<targetId>` (`push/fcm.read.json`). APNs: `apns-push-type: background`, `apns-priority: 5`, `apns-collapse-id: r-<conversationType>-<targetId>`, payload `{aps: {content-available: 1}, type, conversationType, targetId}` без alert и звука (`push/apns.read.json`).

Звонок:

```json
{ "type": "call", "callerId": 2 }
```

- `callerId` — кто звонит; `callId` (строка) появится, когда в протоколе будет номер звонка, — клиент принимает его как необязательный.

Как это лежит у поставщиков (фикстуры собраны кодом сервера):

| | Android (FCM v1) | iOS (APNs) |
|---|---|---|
| Где id | `message.data` — **все значения строки** (`"targetId": "2"`) | верхний уровень payload — **числа** |
| Сообщение | data-only (без блока `notification`), `android.priority: HIGH`, `ttl: 86400s`, `collapse_key: m-<conversationType>-<targetId>` (`push/fcm.message.direct.json`, `.channel.json`) | `apns-push-type: alert`, `apns-topic: <bundle>`, `apns-priority: 10`, `apns-expiration: now+86400`, `apns-collapse-id: m-<conversationType>-<targetId>`; `aps: {alert: {body: "Новое сообщение"}, sound: "default", mutable-content: 1, thread-id: "<conversationType>-<targetId>"}` (`push/apns.message.direct.json`, `.channel.json`) |
| Звонок | `android.priority: HIGH`, `ttl: 30s`, без `collapse_key` (`push/fcm.call.json`) | Серверный формат для будущего PushKit: `apns-topic: <bundle>.voip`, `apns-push-type: voip`, `apns-priority: 10`, `apns-expiration: now+30`, payload без `aps` (`push/apns.call.json`). iOS v1 не регистрирует VoIP-токен и не получает этот тип push. |

Схлопывание: пока устройство недоступно, поставщик держит для переписки только последнее уведомление; на iOS новое уведомление той же переписки заменяет показанное. Клиент принимает и неизвестные поля, и неизвестный `type` (игнорирует).

## 5. Поведение приложения

**На переднем плане** (сокет открыт, `device_id` передан в `auth`): push о сообщениях не приходит — баннер показывает приложение по полю `notify` кадра (`multi-device.md` §5). Push `read` — снять уведомления переписки и обнулить её непрочитанное. Если уведомление всё же пришло (сокет только что подключился), приложение его не показывает, когда сообщение уже есть в модели (`messageId`) или открыта эта переписка.

**В фоне / выгружено:**
- Android: `FirebaseMessagingService.onMessageReceived` (data-сообщение высокого приоритета будит приложение) → `GET /api/messages?conversationType=…&targetId=…&afterId=<messageId − 1>` (или `/api/sync`) своим токеном → локальное уведомление с именем и текстом, канал уведомлений «Сообщения», группировка по переписке. Нет сети/токен мёртв/сообщение удалено — общий текст «Новое сообщение» без подробностей (или ничего, если удалено). Android может понижать приоритет приложению, которое на high-priority data не показывает уведомление, — показывать всегда.
- iOS: APNs показывает системное уведомление с общим текстом «Новое сообщение» и группирует его по `thread-id`. При доставке на экран блокировки текст и имя отправителя не загружаются. После запуска приложения оно получает содержимое с сервера обычной синхронизацией. Получение содержимого до показа через Notification Service Extension — будущая отдельная задача.
- Нажатие — открыть переписку (`conversationType`, `targetId`), затем обычная синхронизация.
- Значок (badge) сервер не ставит: счётчик приложение считает само (`unread_snapshot`).

**Звонок:**
- iOS: входящие звонки при закрытом приложении не поддерживаются в v1. PushKit/CallKit отсутствуют; их добавление требует отдельной интеграции, включая показ каждого VoIP-push через CallKit. Формат APNs VoIP на сервере описывает будущую возможность, а не работающую доставку на iOS.
- Android: высокоприоритетное FCM → обычное уведомление о входящем звонке в канале «Звонки» (без полноэкранного `CallStyle`). Имя звонящего показывается, если приложение успело получить его с сервера; иначе показывается общий текст «Звонит сотрудник». Уведомление автоматически снимается через 30 с. Нажатие открывает приложение и подключает сокет, который получает тот же `call_offer`.
- Принять/отклонить — обычные `call_answer` / `call_rejected` по сокету.

## 6. Надёжность и ограничения

- Доставка асинхронная: путь сообщения уведомления не ждёт (очередь с ограниченной параллельностью). Временные ошибки поставщика — повтор с растущей паузой (до 4 попыток), недействительный токен (FCM `UNREGISTERED`; APNs 410, `BadDeviceToken`) — удаляется. Ответы, говорящие об ошибке настройки сервера (FCM `SENDER_ID_MISMATCH`, 404 без кода; APNs `DeviceTokenNotForTopic` и ошибки токена поставщика), токены **не** удаляют — иначе одна опечатка в настройках стёрла бы все; они один раз громко пишутся в журнал. Перед каждой попыткой, включая повторы, сервер заново проверяет, что токен всё ещё у того же сотрудника и того же сеанса и сеанс действует; иначе доставка снимается. Сеанс, продлённый между попытками (`/api/auth/refresh`), — тот же сеанс: повтор идёт дальше по новому токену сеанса. Push — **подсказка, а не канал доставки**: уведомление может не прийти, прийти дважды или с опозданием; источник правды — `/api/sync`.
- Очередь в памяти процесса: перезапуск сервера теряет неотправленные уведомления (сообщения при этом не теряются).
- Поставщики и их адреса зашиты в код (`fcm.googleapis.com`, `oauth2.googleapis.com`, `api.push.apple.com`, `api.sandbox.push.apple.com`); настройками их не сменить.
