# Один сотрудник на нескольких устройствах

Единый документ для **всех** клиентов — настольного (Electron), Android и iOS — о том, как ведёт себя сотрудник, у которого CentyChat открыт сразу на компьютере и на телефоне. Протокол кадров — `ws-protocol.md`, модель доставки — `delivery-state.md`, push — `push.md`; здесь — как они складываются, когда устройств несколько. Решения владельца от 2026-10-02.

Исполняемая форма правил уведомлений — `reference/notify-decision.mjs` (сервер использует тот же код: `server/src/push/notify-decision.js`, общий блок совпадает байт в байт) и векторы `fixtures/notify/*.json`. Реализация сервера — `server/src/ws/server.js`, `server/src/push/`. Тесты сервера — `server/test/multi-device.test.js`, `server/test/notify-decision.test.js`.

## 1. Модель

- **Источник правды — сервер.** Сообщения, правки, удаления, прочтение, «Не беспокоить» и присутствие хранит и рассылает сервер. Клиент применяет то, что пришло (живой кадр, страница `/api/sync`, страница истории), и ничего не «додумывает» между устройствами: одно устройство узнаёт о действиях на другом **только от сервера**.
- Каждое устройство — отдельный сокет (до 8 на сотрудника). Кадры, адресованные сотруднику, уходят **всем** его сокетам (кроме оговорённых ниже случаев «кроме отправившего»).
- Устройство без связи догоняет всё через `GET /api/sync` со своего курсора (`delivery-state.md` §6): курсор — номер изменения на сервере, общий для всех устройств, и любое устройство с того же курсора получает ровно те же изменения.

## 2. Присутствие и «Не беспокоить»

Правило владельца: приложение открыто (передний план) — «В сети»; свёрнуто / в фоне / компьютер простаивает — «Отошёл»; вручную выбирается только «Не беспокоить». Клиент шлёт только `{type: "presence", state: "online" | "away"}` и `set_dnd`.

- **Присутствие — у каждого сокета своё.** Новый сокет входит «в сети» (или «отошёл», если в `auth` передано `presence: "away"`, §3).
- **Итог по сотруднику:** «в сети», если **хоть один** сокет «в сети»; «отошёл» — только если **все** сокеты «отошёл»; «не в сети» — сокетов нет. Телефон, ушедший в фон, не делает «отошёл» человека, который печатает за компьютером.
- Закрылся сокет, другие остались — итог пересчитывается (ушло единственное устройство «в сети» → «отошёл»); закрылся последний — «не в сети», как раньше.
- **«Не беспокоить» — одно на сотрудника**, общее для всех устройств, переживает переподключения и показывается поверх итога (`dnd`). Включили на телефоне — `user_status_changed {status: "dnd"}` приходит всем, в том числе всем сокетам самого сотрудника: остальные его устройства обновляют переключатель по этому кадру. Выключили — показывается текущий итог («в сети» или «отошёл»).
- `user_status_changed` рассылается, только когда **итог** действительно сменился (и при каждом входе сокета — как раньше).
- Старые кадры `set_status` / `status_update` работают: `online`/`away` — сигнал этого сокета, `dnd` — включение режима.
- Текст статуса (`customStatus`) — у сотрудника, а не у устройства.

## 3. Какое устройство за каким сокетом

Кадр `auth` принимает два **необязательных** поля (старые клиенты их не шлют и работают как раньше):

```json
{ "type": "auth", "token": "<JWT>", "device_id": "android-7f3a…", "platform": "android", "presence": "away" }
```

| Поле | Значения | Зачем |
|---|---|---|
| `device_id` | `[A-Za-z0-9._:-]{1,128}` — **тот же**, что в `/api/auth/knock` и `POST /api/devices/push-token` | сервер узнаёт, что этот сокет — то самое устройство, на которое зарегистрирован push: устройство с сокетом «в сети» получает баннер по сокету, а не push |
| `platform` | `desktop` / `android` / `ios` / `web` | справочно (журнал, будущие правила) |
| `presence` | `online` (по умолчанию) / `away` | телефон, переподключившийся **в фоне**, сразу входит «отошёл» и не перебивает push |

Недопустимое значение — не ошибка: поле игнорируется. **Мобильные клиенты обязаны** передавать `device_id` (иначе их сокет не связан с push-токеном, и телефон на переднем плане получит и баннер, и push) и `presence: "away"`, если подключаются в фоне.

## 4. Сигнал «смотрю этот чат» (`viewing`)

Клиент → сервер, новый кадр (предел — 20 в секунду на сокет, сверх — молча отбрасывается):

```json
{ "type": "viewing", "conversationType": "direct", "targetId": 5 }
{ "type": "viewing", "conversationType": null }
```

- `targetId` — переписка с точки зрения этого сотрудника: id собеседника или id канала (то же, что в `mark_read`). `conversationType: null` — ни один чат не открыт.
- Сервер хранит `viewing` **у сокета**. Сокет «смотрит чат C», только пока его присутствие `online`. Сервер сам снимает `viewing` при закрытии сокета, при `presence: "away"` и при новом `auth`. Недопустимый кадр (`conversationType` не `direct`/`channel`, `targetId` не целое > 0) ничего не меняет.
- **Правило клиента (одинаково на всех платформах):**
  1. слать `viewing {C}`, когда экран/окно чата C открыто **и** приложение на переднем плане **и** окно в фокусе (настольный клиент: открыт раздел переписок, окно в фокусе, не свёрнуто);
  2. слать `viewing {null}`, когда ушли из чата (список, другой экран), окно потеряло фокус или свёрнуто/скрыто, приложение ушло в фон, сотрудник простаивает (перед `presence: "away"` или вместо него — сервер снимет и сам);
  3. после каждого `auth_success` и после возврата `presence: "online"` — прислать текущее состояние заново (сервер его сбросил);
  4. пока смотрит чат C — `mark_read` C сразу на каждое новое чужое сообщение C; при открытии чата и при возврате на передний план — тоже `mark_read`.
- Слать только при **смене** состояния (не на каждую перерисовку).

## 5. Кому уведомление о новом сообщении

Правило владельца: уведомление зависит от того, **смотрит ли сотрудник этот чат**.

- Чат открыт на переднем плане **на любом** устройстве сотрудника — **никому** ничего: он видит сообщения вживую.
- Сотрудник вне окна этого чата (другой чат, список, другой экран, приложение свёрнуто, компьютер простаивает, приложение закрыто) — **уведомление приходит**, даже если приложение открыто и показывает «В сети».
- «Не беспокоить» гасит всё. Свои сообщения не уведомляют никогда.

Решение принимается **одной чистой функцией** для каждого получателя:

```
decideMessageNotification({ recipientId, dnd, message: { conversationType, targetId, senderId },
                            sockets: [{ id, deviceId, presence, viewing }], pushDevices: [{ id }] })
  -> { reason: 'own' | 'dnd' | 'viewing' | null, push: [deviceId…], banner: [socketId…], quiet: [socketId…] }
```

По порядку:

1. автор — получатель → `reason: "own"`, никому ничего;
2. «Не беспокоить» → `reason: "dnd"`, никому ничего;
3. хоть один сокет `online` смотрит **этот** чат (тот же `conversationType` **и** `targetId`; для личного — собеседник, т. е. автор) → `reason: "viewing"`, никому ничего;
4. иначе (`reason: null`):
   - **баннер** — каждому сокету `online`, а также сокету `away`, у устройства которого нет push (настольный клиент, телефон без токена);
   - **без баннера** (`quiet`) — сокет `away` на устройстве с push: уведомит push;
   - **push** — каждому устройству с push, у которого нет сокета `online` (нет сокета вовсе или он в фоне).

| Ситуация (вектор) | Компьютер | Телефон |
|---|---|---|
| чат открыт на компьютере, телефон в кармане (01) | — | — |
| чат открыт на телефоне, компьютер в другом чате (02) | — | — |
| компьютер в другом чате, телефон без сокета (03) | баннер | push |
| оба на переднем плане в списке (04) | баннер | баннер |
| компьютер простаивает с открытым чатом (05) | баннер | push |
| телефон в фоне с живым сокетом, компьютер смотрит чат (06) | — | — |
| «Не беспокоить» (07) | — | — |
| своё сообщение (08) | — | — |
| канал 7; компьютер в канале 8, iPhone в личном с id 7 (09) | баннер | баннер |
| канал открыт на iPhone (10) | — | — |
| сокетов нет (11) | — | push |
| старый клиент без `viewing`/`device_id` (12) | баннер | push |
| телефон в фоне с сокетом и push, компьютер в списке (13) | баннер | push (кадр без баннера) |
| телефон на переднем плане на другом экране (14) | — | баннер |
| телефон в фоне, push нет (15) | — | баннер |
| два телефона: Android в списке, iPhone без сокета (16) | — | Android баннер, iPhone push |
| всё в фоне, на обоих «открыт» чат (17) | баннер | push (кадр без баннера) |

**Как решение доходит до клиента.** Кадры нового сообщения (`direct_message` / `channel_message` и `new_message`) несут новое поле **`notify`** (boolean) — своё для каждого сокета: `true` — показать баннер / локальное уведомление, `false` — не показывать. Своё эхо и повтор отправки (тот же `client_msg_id`) — всегда `false`. Счётчик непрочитанного от `notify` **не зависит** (`delivery-state.md` §7.8). Сервер без этого поля (старый) — клиент решает сам по прежнему правилу: не своё, чат не открыт здесь, не «Не беспокоить».

**Push.** Сервер ставит в очередь уведомление каждому получателю с `reason: null`; какие устройства его получат, очередь решает **той же функцией** с сокетами на момент проверки — при раздаче по устройствам и ещё раз перед каждой попыткой доставки, в том числе повтором (сотрудник мог открыть чат, подключиться или включить «Не беспокоить», пока задание ждало). Устройство с push — строка токена `push_tokens` с её `device_id`; токен без `device_id` — отдельное устройство, которое никогда не совпадает с сокетом.

**Звонки** — без изменений (`push.md` §3): вызов звонит на все сокеты; push о звонке — только если у вызываемого нет ни одного сокета; отвечает одно устройство, остальным — `call_end … answered_elsewhere`.

## 6. Прочтение на одном устройстве — на всех

Правило владельца: прочитано на любом устройстве (телефон или компьютер) — прочитано у сотрудника; остальные устройства снимают непрочитанное; уже показанное уведомление на другом устройстве по возможности убирается.

- `mark_read` с одного сокета, если что-то **действительно** прочитано (в личном — есть вновь прочитанные входящие; в канале — позиция прочтения сдвинулась), даёт:
  - собеседнику — прежний `messages_read` (только личные);
  - **остальным сокетам читателя** (кроме отправившего `mark_read`) — новый кадр `conversation_read`:

```json
{ "type": "conversation_read", "conversationType": "direct", "targetId": 5, "byUserId": 2, "at": "2026-10-02T09:00:00.000Z", "messageIds": [41, 42] }
{ "type": "conversation_read", "conversationType": "channel", "targetId": 7, "byUserId": 2, "at": "2026-10-02T09:00:00.000Z", "lastReadId": 120 }
```

  `targetId` — переписка с точки зрения читателя (собеседник / канал); `byUserId` — сам читатель; `at` — время сервера (ISO); `messageIds` — только у личных (вновь прочитанные входящие), `lastReadId` — только у каналов (новая позиция прочтения). Пустая отметка не рассылается.
  - устройствам читателя с push, у которых **нет** сокета `online`, — тихий push **`read`** (`push.md` §4, `decideReadDismissal`), но только по переписке, о которой этому сотруднику уходил push о сообщении после прошлого прочтения (иначе снимать нечего; память об этом — в процессе сервера, после перезапуска снятие не придёт). Приложение снимает показанные уведомления этой переписки. Доставка — как получится: Apple тихие push не гарантирует.
- Устройство без связи узнаёт о прочтении из `/api/sync` (личные: `delivery_status = "read"` у входящих) и из `unread_count` списков (каналы) — `delivery-state.md` G5.
- Порядок от сервера делает «обнулить счётчик переписки» точным: сообщение, сохранённое **до** обработки `mark_read`, вошло в прочитанное; сохранённое **после** — придёт кадром **после** `conversation_read` и снова увеличит счётчик.

## 7. Идемпотентность и порядок

1. **Применять по `id` сообщения.** `direct_message` и `new_message` — один и тот же объект дважды; повтор кадра, эхо после повтора отправки, страница синхронизации — тот же `id`, без второго экземпляра.
2. **Своё эхо — по `client_msg_id`.** Эхо своего сообщения приходит **всем** сокетам автора. Отправившее устройство сопоставляет его со своей записью outbox по `client_msg_id`; другое устройство автора просто добавляет сообщение (своё, без счётчика и уведомления). Повтор отправки тем же ключом — та же запись, получателям не рассылается.
3. **Правка — только если новее.** `message_updated` применяется, если `updated_at` новее хранящегося и сообщение не надгробие (`delivery-state.md` T31). Две правки с разных устройств: побеждает та, что сервер записал последней (её `updated_at` не раньше).
4. **Надгробие окончательно.** `message_deleted` (или `is_deleted = 1` в синхронизации) превращает сообщение в надгробие навсегда, какой бы `updated_at` ни пришёл потом; правка удалённого на сервере отклоняется (`error` `MESSAGE_DELETED`). Удаление с одного устройства и правка с другого почти одновременно: сервер обрабатывает их в своём порядке; если удаление было раньше — правка отклонена; если позже — надгробие приходит после `message_updated`, и `updated_at` надгробия не раньше правки.
5. **Кадры одного сокета обрабатываются по очереди** (send/edit/delete/cancel/mark_read, `ws-protocol.md` §2.3) — у одного устройства не перемешиваются. Между устройствами порядок задаёт сервер: какой кадр он обработал первым.
6. **Статусы не понижаются:** `read` не откатывается в `delivered`.
7. **Счётчик непрочитанного** растёт только от живых кадров нового чужого сообщения не открытой здесь переписки; обнуляется при открытии переписки, `conversation_read`, `unread_snapshot` (`delivery-state.md` §7.8).
8. **После переподключения** — `/api/sync` с курсора, затем `refresh_conversation_lists` → `unread_snapshot`; затем заново `viewing` и, если открыт чат, `mark_read`.

## 8. Что делать клиенту на каждый кадр

| Кадр (сервер → клиент) | Что сделать |
|---|---|
| `auth_success` | начать синхронизацию (`/api/sync`); прислать текущее `viewing`; если в фоне — `presence: "away"` (или передать `presence: "away"` в `auth`) |
| `direct_message` / `channel_message` / `new_message` | применить по `id` (дубль — пропустить); своё — сопоставить по `client_msg_id`; чужое в открытой и видимой переписке — `mark_read`; иначе `unread + 1`; баннер/локальное уведомление — только если `notify === true` (нет поля — прежнее локальное правило) |
| `message_updated` | применить, если новее по `updated_at` и не надгробие |
| `message_deleted` | надгробие (окончательно); снять уведомление этого сообщения, если показано |
| `message_status_updated` | поднять статус своего личного сообщения (не понижать) |
| `messages_read` | свои сообщения переписки с `byUserId` → `read` |
| `conversation_read` | обнулить непрочитанное переписки (`conversationType`, `targetId`); снять её показанные уведомления |
| `user_status_changed` | обновить статус сотрудника; свой `dnd` — переключатель «Не беспокоить» на этом устройстве |
| `user_typing` | показать «печатает…» (приходит всем устройствам собеседника, не своим) |
| `call_offer` / `call_end` (`answered_elsewhere`) | `push.md` §3, §5 — без изменений |
| push `message` | Android: показать уведомление (текст — с сервера); iOS — расширение уведомлений. Если сообщение уже есть в модели и прочитано или переписка открыта — не показывать |
| push `read` | снять показанные уведомления переписки (`conversationType`, `targetId`); обнулить её непрочитанное локально (подтвердит следующий `unread_snapshot`) |

## 9. Все правила одним списком

1. Источник правды — сервер; устройство узнаёт о действиях на другом только от сервера.
2. Каждое устройство — свой сокет; кадры сотруднику — всем его сокетам, кроме оговорённых «кроме отправившего».
3. Присутствие — у каждого сокета; новый сокет входит «в сети» (или «отошёл» по `presence` в `auth`).
4. Итог: «в сети», если хоть один сокет «в сети»; «отошёл», если все «отошёл»; «не в сети» — сокетов нет.
5. Уход сокета пересчитывает итог; рассылка `user_status_changed` — только при смене итога (и при входе).
6. «Не беспокоить» — одно на сотрудника, общее для устройств, переживает переподключения, показывается поверх итога.
7. Клиент шлёт только `presence online/away` и `set_dnd`; `set_status`/`status_update` старых клиентов работают.
8. Мобильный клиент передаёт в `auth` свой `device_id` (тот же, что при регистрации push) и `platform`.
9. Клиент шлёт `viewing {C}`, когда чат C открыт на переднем плане и в фокусе; `viewing {null}` — когда нет; после `auth_success` и возврата «в сети» — заново.
10. `viewing` сокета действует, только пока сокет «в сети»; сервер снимает его при `away`, закрытии и новом `auth`.
11. Пока чат открыт и виден — `mark_read` на каждое новое чужое сообщение; при открытии и возврате на передний план — тоже.
12. Своё сообщение не уведомляет никогда.
13. «Не беспокоить» гасит все уведомления (баннеры и push); счётчики остаются.
14. Чат открыт на переднем плане на любом устройстве — никому никаких уведомлений о нём.
15. Иначе: баннер — каждому сокету «в сети» и сокету в фоне без push; push — каждому устройству с push без сокета «в сети».
16. Решение — одна функция (`notify-decision`); сервер вызывает её при рассылке и перед каждой попыткой push; платформы проходят те же векторы.
17. Клиент показывает баннер, только если в кадре `notify: true`; без поля — по прежнему локальному правилу.
18. Счётчик непрочитанного не зависит от `notify`.
19. Прочтение на одном устройстве: собеседнику — `messages_read`; остальным устройствам читателя — `conversation_read`; устройствам с push без сокета «в сети», которым уходил push о переписке, — тихий push `read`.
20. Пустая отметка прочтения ничего не рассылает.
21. Через Google/Apple — только id; `read` несёт тип и id переписки.
22. Сообщения применяются по `id`; своё эхо — по `client_msg_id`; повтор отправки — та же запись.
23. Правка — только если новее по `updated_at` и не надгробие; надгробие окончательно.
24. Устройство без связи догоняет через `/api/sync` со своего курсора; любое устройство с того же курсора получает то же.
25. Звонки — как раньше: звонят все сокеты, push о звонке — только без сокетов, отвечает одно устройство.

## 10. Чек-лист платформы (Android и iOS одинаково)

- [ ] `auth`: передавать `device_id` (тот же, что в `knock` и `/devices/push-token`) и `platform`; при подключении в фоне — `presence: "away"`.
- [ ] Жизненный цикл: передний план → `presence: online`; фон → `presence: away` (сервер сам снимет `viewing`).
- [ ] `viewing {conversationType, targetId}` при открытии экрана чата на переднем плане; `viewing {null}` при уходе с экрана, в фон, при блокировке экрана; заново после `auth_success` и возврата на передний план; только при смене.
- [ ] `mark_read` сразу на новое чужое сообщение открытого чата и при открытии/возврате.
- [ ] Баннер в приложении / локальное уведомление из кадра — только при `notify === true`; без поля — локальное правило.
- [ ] `conversation_read` — обнулить счётчик переписки, снять её уведомления (Android: `NotificationManager.cancel` по тегу/группе переписки; iOS: `removeDeliveredNotifications` по `thread-id` `<conversationType>-<targetId>`).
- [ ] Push `read` (Android — data-сообщение обычного приоритета в `onMessageReceived`; iOS — `application(_:didReceiveRemoteNotification:fetchCompletionHandler:)` с `content-available`) — то же снятие и обнуление; ничего не показывать.
- [ ] Push `message` при живом сокете на переднем плане не приходит; если всё же пришёл — не показывать, когда сообщение уже есть или переписка открыта (дедуп по `messageId`).
- [ ] Прогнать векторы `fixtures/notify/*.json` своим решением (если платформа повторяет его локально) и фикстуры `ws/conversation_read.*`, `push/*.read.json` декодером.

## 11. Совместимость

- Новые поля и кадры аддитивны. Старые клиенты игнорируют `notify`, `conversation_read` (настольный клиент — веткой `default` обработчика кадров), не шлют `viewing` и `device_id`: их сокеты считаются «не смотрят» и «без устройства» (вектор 12).
- Старый сервер не знает `viewing` (кадр отбрасывается как неизвестный, без ответа) и не шлёт `notify`/`conversation_read`: клиенты работают по прежнему локальному правилу.
- Настольные оболочки 1.0.0 загружают новый интерфейс с сервера и сразу шлют `viewing`.

## 12. Открытые вопросы

- Push о **звонке** по-прежнему уходит, только если у вызываемого нет ни одного сокета: компьютер простаивает (сокет жив) — звонит компьютер, телефон в кармане не будится. Правило «как у сообщений» для звонков требует отдельного решения (одновременный звонок по сокету и через PushKit/FCM, снятие на ответившем устройстве).
- Память «кому уходил push о переписке» — в процессе сервера: после перезапуска тихий `read` по старым уведомлениям не придёт (уведомление снимется при открытии приложения).
- Тихие push на iOS не гарантированы и ограничиваются системой.
