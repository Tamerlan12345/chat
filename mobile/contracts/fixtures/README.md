# Общие JSON-фикстуры мобильного контракта

Единый источник правды для iOS (Swift) и Android (Kotlin): ответы и WebSocket-кадры **настоящего сервера** CentyChat, снятые сценарием и нормализованные. Контракт в прозе — `../ws-protocol.md`, `../openapi.yaml`.

## Обязательное правило для платформ

**Каждая платформа обязана декодировать КАЖДУЮ фикстуру в unit-тестах** (тест обходит `fixtures/**/*.json` по `manifest.json`, а не по заранее заданному списку, чтобы новая фикстура сразу попадала под проверку) и сверять ключевые поля с ожидаемыми значениями. Декодер должен:

- игнорировать неизвестные поля (сервер добавляет поля аддитивно);
- принимать `null` и отсутствие ключа для необязательных полей (например, у `user_status_changed` в состоянии `offline` нет `customStatus`);
- читать `0/1` как boolean для `is_active`, `is_deleted`, `must_change_password`;
- читать `client_msg_id` сообщения как строку или `null` (есть во всех формах сообщения), `next_cursor` из `/api/sync` — как непрозрачную **строку** (не разбирать);
- читать `announcementId` в `announcement_acknowledged` как **строку**, `at`/`retryAt` в событиях побудки как **epoch в миллисекундах**, остальные времена как ISO-8601 UTC;
- не падать на служебных полях `user` (`permissions_json`, `token_version`, `bound_ip`, `last_login_ip`…).

## Именование

```
fixtures/
  manifest.json                     описание каждого файла: how/why
  http/<область>.<ответ>.json       тело ответа REST, например http/auth.knock-paired.json
  ws/<событие>.json                 кадр сервер -> клиент, как на проводе
  ws/<событие>.<вариант>.json       несколько форм одного события (new_message.direct / .channel)
```

- `<событие>` — значение поля `type` кадра, дословно (`new_message`, `call_end`, …); вариант — условие, при котором форма отличается (`connection_lost`, `cooldown`, `invalid_token`).
- Файл содержит **только тело** (для HTTP — JSON ответа без статуса и заголовков; статус и маршрут — в `manifest.json`).
- `manifest.json`: для `http` — `method`, `path`, `status`; для `ws` — `event`, `direction` (`server->client`), `trigger` (что сделал клиент/админ, чтобы сервер прислал кадр); у всех — `description` по-русски.

Полное соответствие «событие → файл» — `../ws-protocol.md` §7.

`reducers/` — не ответы сервера, а табличные векторы клиентского редьюсера доставки (`../delivery-state.md`); в `manifest.json` не входят, декодирующие тесты их пропускают, `capture-fixtures.mjs --write` их не трогает. Формат и обязательный прогон на платформах — `reducers/README.md`.

## Нормализация (что в фикстурах не настоящее)

| Что | Как заменено |
|---|---|
| `token` | константа в форме JWT (не подписанная, не принимается сервером) |
| время ISO-8601 | `2026-10-02T09:00:00.000Z` + порядковый сдвиг в секундах внутри файла (порядок `created_at` < `updated_at` сохранён, формат и точность — как у сервера) |
| `at` / `retryAt` (побудка, epoch мс) | `1790931600000` / `+60000` |
| `uin` | `1000 + id` (на сервере случайный) |
| `storedFilename` | константа |
| эпоха в `next_cursor` (`<эпоха>.<номер>`) | `5e7a1c0d9b3f4a62` (на сервере случайная для каждой базы) |

Идентификаторы (`id`, `messageId`, …) не меняются: сценарий всегда выполняется на пустой базе, поэтому они повторяются. Тексты — русские, реалистичные.

## Как фикстуры получаются

`node mobile/dev/capture-fixtures.mjs --write` поднимает **отдельный процесс сервера** (пустая база во временном каталоге, случайный порт, без TLS), заполняет его данными dev-стенда (`mobile/dev/seed.mjs`: `alice`, `bob`, канал `#mobile-dev`, сообщения, вложение, оповещение) и проигрывает сценарий как настоящие клиенты — REST через `fetch`, WebSocket через `ws`: вход, `knock`/`claim`, отправка (с `client_msg_id` и без), повтор отправки и ошибки ключа, страница `afterId`, синхронизация `/api/sync` (начало, страница с правкой/удалением/сменой статуса, недействительный курсор), «доставлено» после переподключения получателя, правка, удаление, прочтение, набор текста, статусы, DND, звонки, побудка, каналы, оповещения, выход, ошибки авторизации, смена прав роли. Каждый нужный ответ или кадр сохраняется. Ничего не придумывается руками.

Режимы:

```bash
node mobile/dev/capture-fixtures.mjs --write   # перезаписать fixtures/** (README.md не трогается)
node mobile/dev/capture-fixtures.mjs --check   # сравнить с закоммиченными, код выхода 1 при расхождении
```

Требуется Node 22+ и `npm install` в `server/`. Время запуска из командной строки — 15–20 секунд (замер 2026-10-02 на Windows: 16 с для `--write`), из них заметная часть — старт отдельного процесса сервера и серия неудачных `auth` в конце сценария (до предела `RATE_LIMITED`). Тест дрейфа в `npm test` проигрывает тот же сценарий за 7–10 секунд (сервер уже прогрет); его предел — 180 секунд.

## Защита от дрейфа

`server/test/mobile-contract-fixtures.test.js` (входит в `cd server && npm test`) заново снимает фикстуры с текущего кода сервера и сравнивает с закоммиченными по **набору ключей и типам значений** (`null` — отдельный тип, значения не сравниваются). Тест падает, если:

- сериализатор сервера добавил, убрал или переименовал поле, либо поле стало/перестало быть `null`;
- появилась или исчезла фикстура/событие;
- не покрыто событие из обязательного списка (`auth_success` … `error`);
- `manifest.json` разошёлся со сценарием.

Если изменение сервера **намеренное** — запустить `--write`, просмотреть `git diff mobile/contracts/fixtures`, обновить `ws-protocol.md`/`openapi.yaml` и закоммитить всё вместе; платформы подхватят изменение своими тестами декодирования.
