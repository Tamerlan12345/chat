# Автообновление настольного клиента — инструкция администратора

Дизайн и внутреннее устройство: `docs/superpowers/specs/2026-09-28-autoupdate-design.md`.
Этот документ — только про то, что делает администратор.

## Как это работает в двух словах

Сервер компании раздаёт установщики (`Setup.exe`) сам, без интернета и без
GitHub. Клиенты, поставленные через NSIS-установщик (обычная установка «для
меня»), сами проверяют `/updates/*` на своём сервере, скачивают новую версию,
проверяют её подпись и ставят. Portable-сборка и установка «копией»
(`installer/install.ps1`) не обновляются сами — только показывают
уведомление со ссылкой на скачивание.

## 1. Подготовка сервера и сети

Прежде чем публиковать первый выпуск, нужно сделать три вещи — без любой из
них автообновление либо не заработает у сотрудников, либо у части из них
откажет при загрузке большого файла.

1. **HTTPS с доверенным TLS-сертификатом на сервере.** Клиент ходит на
   `/updates/*` через обычный TLS (`fetch`/`electron-updater`), и если
   сертификат сервера не проходит проверку цепочки доверия (самоподписанный
   или от неизвестного корня), запросы будут падать по сети ещё до всякой
   проверки подписи установщика. Это либо сертификат от публичного
   удостоверяющего центра, либо от корпоративного CA, уже установленного
   на рабочих машинах через доменную политику.

2. **Корневой сертификат Centras на клиентских машинах.** Установщики
   подписаны корпоративным сертификатом (отпечаток
   `0EB61614FC390FCD11BDF8DBFD40BE62EE10862A`, CN=`Centras Insurance (АО
   Сентрас Иншуранс)`), самоподписанным. Пока его нет в «Доверенных корневых
   центрах сертификации» машины, `Get-AuthenticodeSignature` возвращает не
   `Valid` — и клиентская проверка `update-verify.js` (та же проверка, что
   описана в дизайне) откажет ставить обновление, даже если файл настоящий.
   Ставится один раз через `installer/установить-сертификат.ps1` (или
   `.bat`) — от администратора, на всю машину, либо для одного пользователя,
   если прав администратора нет. Это не связано с TLS-сертификатом сервера
   (пункт 1) — это про доверие к подписи `.exe`, а не к сайту.

3. **`client_max_body_size 600m` на прокси перед сервером.** По умолчанию
   nginx (и большинство обратных прокси) режут тело запроса на 1 МБ — а
   установщик весит сотни мегабайт (лимит сервера — `UPDATES_MAX_FILE_MB`,
   по умолчанию 600). Без этой настройки загрузка выпуска через консоль
   администратора будет обрываться с 413 на прокси, даже не дойдя до
   Node.js. Нужна на маршруте `POST /api/admin/updates/releases`; на
   `/updates/*` (сами скачивания у сотрудников) можно не трогать — это
   `GET`.

4. **Адрес сервера на клиентских машинах — политика реестра.** Собранный
   клиент берёт адрес сервера и настройки обновлений только из ключа
   `HKLM\SOFTWARE\Policies\OpenMyChat Enterprise` (писать туда могут только
   администраторы). Нет ключа — используется адрес, зашитый в сборку.
   Переменные окружения и файлы в профиле или в `ProgramData` собранный
   клиент не читает: папку в `ProgramData` может создать любой пользователь
   ПК и увести приложение всех остальных на свой сервер.

   Файл `%ProgramData%\OpenMyChat Enterprise\client.json`, который писал
   `configure-client.ps1` в пилотной версии, теперь игнорируется: запишите
   политику реестра (перезапустите `configure-client.ps1` с нужными
   параметрами) и удалите этот файл.

   | Значение | Тип | Смысл |
   |---|---|---|
   | `ServerUrl` | `REG_SZ` | Адрес сервера, только `https://`, без имени и пароля. Кириллический домен — в punycode (`https://xn--…`): `configure-client.ps1` переводит его сам, в групповой политике и `reg add` пишите punycode. |
   | `UpdatesEnabled` | `REG_DWORD` | `1` — обновления включены (так же, если значения нет), `0` — выключены на этой машине. |
   | `UpdateChannel` | `REG_SZ` | `stable` (по умолчанию) или `beta`. |

   Значение другого типа или с ошибкой клиент игнорирует (выключатель с
   ошибкой считается выключенным) и пишет причину в свой журнал
   `%APPDATA%\OpenMyChat Enterprise\logs\main.log` (строки `machine policy:`).

   **На одной машине** — `installer/configure-client.ps1` от администратора
   (или `настроить-клиент.bat` с теми же параметрами):

   ```powershell
   configure-client.ps1 -ServerUrl https://chat.company.kz [-Channel stable|beta] [-DisableUpdates | -EnableUpdates]
   ```

   Без `-ServerUrl` уже записанный адрес не меняется, без `-Channel` — канал.
   То же вручную:

   ```bat
   reg add "HKLM\SOFTWARE\Policies\OpenMyChat Enterprise" /v ServerUrl /t REG_SZ /d https://chat.company.kz /f
   reg add "HKLM\SOFTWARE\Policies\OpenMyChat Enterprise" /v UpdatesEnabled /t REG_DWORD /d 1 /f
   reg add "HKLM\SOFTWARE\Policies\OpenMyChat Enterprise" /v UpdateChannel /t REG_SZ /d stable /f
   ```

   **На весь домен — групповой политикой** (административные шаблоны не
   нужны): «Управление групповой политикой» → объект GPO, связанный с OU
   компьютеров → «Конфигурация компьютера» → «Настройка» → «Конфигурация
   Windows» → «Реестр» → «Создать» → «Элемент реестра», по элементу на
   значение:

   | Поле | ServerUrl | UpdatesEnabled | UpdateChannel |
   |---|---|---|---|
   | Действие | Обновить | Обновить | Обновить |
   | Куст | `HKEY_LOCAL_MACHINE` | `HKEY_LOCAL_MACHINE` | `HKEY_LOCAL_MACHINE` |
   | Путь раздела | `SOFTWARE\Policies\OpenMyChat Enterprise` | то же | то же |
   | Имя параметра | `ServerUrl` | `UpdatesEnabled` | `UpdateChannel` |
   | Тип параметра | `REG_SZ` | `REG_DWORD` | `REG_SZ` |
   | Значение | `https://chat.company.kz` | `1` (десятичное) | `stable` |

   Клиент читает политику при запуске — после `gpupdate` сотрудникам нужно
   перезапустить приложение (или дождаться следующего входа в Windows).

## 2. Выпуск новой версии

1. В `desktop/package.json` поднять `version` (semver, `x.y.z` или
   `x.y.z-beta.1`).
2. `cd desktop && npm run release` — собирает `dist`/NSIS/portable и
   подписывает `Setup.exe` закреплённым сертификатом (`npm run dist && npm
   run sign`).
3. `npm run publish:update` — проверяет, что `Setup.exe` подписан именно
   закреплённым сертификатом и что его sha512 совпадает с `latest.yml`
   (иначе где-то в цепочке файл переподписали или пересобрали не полностью),
   и собирает `desktop/release/update-<version>/` (`latest.yml`, `Setup.exe`,
   `.blockmap`, `Portable.exe`, `README.txt` — последний только для
   человека, на сервер он не загружается). Сверяется только закреплённый
   отпечаток `0EB61614FC390FCD11BDF8DBFD40BE62EE10862A`; переменная
   `MYCHAT_SIGN_THUMBPRINT` (тестовая подпись) здесь не действует — такой
   выпуск клиенты всё равно отвергли бы.
   - Без параметров скрипт просто готовит папку и печатает, что с ней
     делать дальше (см. ниже).
   - С `-Server https://...` — сразу загружает выпуск
     (`POST /api/admin/updates/releases`, поля `yml`, `setup`, `blockmap`,
     `portable` и `notes`). Токен супер-администратора — в переменной
     `MYCHAT_UPDATE_TOKEN` (параметр `-Token` тоже работает, но остаётся в
     истории PowerShell); заметка к выпуску — `-Notes "..."`:

     ```powershell
     $env:MYCHAT_UPDATE_TOKEN = '<токен>'
     npm run publish:update -- -Server https://chat.company.kz -Notes "Исправлена передача файлов"
     ```
4. Либо отдать готовую папку `update-<version>/` серверу вручную — одним из
   двух способов:
   - **Консоль администратора** — вкладка «Обновления» (только
     супер-администратор), раздел «Загрузить релиз»: выбрать `latest.yml`,
     установщик, `.blockmap` и portable из папки. Удобно для небольших
     сетей и когда консоль доступна с той же машины, где собран выпуск.
   - **Папка inbox на сервере** — скопировать папку `update-<version>/`
     **целиком, подпапкой** в `data/updates/inbox/` (по сети, флешкой,
     `scp` — как угодно), чтобы получилось
     `data/updates/inbox/update-<version>/latest.yml` и т. д.: файлы,
     положенные прямо в `inbox/`, сервер не видит. Затем на вкладке
     «Обновления» в разделе «Папка inbox» нажать «Импортировать»
     (`POST /api/admin/updates/inbox/:name/import`). Сервер проверяет
     содержимое так же, как при загрузке через консоль: разбор
     `latest.yml`, semver версии, имена файлов, `MZ`-сигнатура, совпадение
     sha512 и размера.

   **Для больших выпусков предпочитайте `inbox/`, а не загрузку через
   консоль.** У Node.js по умолчанию 300-секундный тайм-аут на запрос; на
   медленном канале передача ~600 МБ через HTTP из консоли администратора
   может в этот тайм-аут не уложиться и оборваться на середине. Копирование
   файла напрямую в `inbox/` (по локальной сети, без HTTP) этой проблемы не
   имеет — сервер просто читает файл с диска при импорте.

Импорт (из консоли и из `inbox/`) пишется в журнал аудита
(`update_release_imported`, поля `version`, `sha512`, `size`).

## 3. Раздача: проценты, каналы, обязательная версия

Политика раздачи — одна на весь сервер, редактируется в консоли
(«Обновления» → «Политика», либо `PUT /api/admin/updates/policy`):

```json
{
  "enabled": true,
  "channels": {
    "stable": { "target": "1.2.0", "rolloutPercent": 25 },
    "beta":   { "target": "1.3.0-beta.1", "rolloutPercent": 100 }
  },
  "minVersion": "1.1.0",
  "checkIntervalMinutes": 240,
  "message": "Исправлена передача файлов"
}
```

- **`rolloutPercent`** (0–100) — доля парка канала, которой предлагается
  `target`. Раздача делается на сервере (не через `stagingPercentage`
  electron-updater): каждый компьютер попадает в одну из 100 «корзин» по
  хэшу своего случайного `installId` и версии-цели, поэтому один и тот же
  компьютер стабильно либо получает выпуск, либо нет, пока цель не
  сменится. Поднимайте постепенно — 5 → 25 → 50 → 100 — и следите за
  вкладкой «Парк» между шагами.
- **`minVersion`** — версии ниже неё получают обновление как **обязательное**
  (`mandatory = clientVersion < minVersion`): такой клиент увидит диалог
  «Обязательное обновление… Перезапуск через 5 минут» с одной отсрочкой, а
  не просто предложение обновиться. `minVersion` не может быть больше
  `target` канала `stable` — иначе обязательными оказались бы версии выше
  предлагаемой.
- **`message`** — короткая заметка о выпуске, ≤ 500 символов, показывается
  в интерфейсе клиента.
- **`checkIntervalMinutes`** (30–1440) — как часто клиенты сами проверяют
  обновления (со случайным сдвигом ±15 %, чтобы не создавать залп запросов
  ровно по расписанию).

## 4. Откат

Намеренно нет кнопки «откатить на предыдущую версию» и не бывает выката
номером ниже уже выпущенного. Клиент требует `allowDowngrade=false` и
дополнительно сверяет `ProductVersion` подписанного файла: ставит только
версию **строго больше** текущей. Это защита от подсовывания старой,
подписанной, но уязвимой сборки взамен новой.

Если новый выпуск оказался плохим — публикуйте **следующую** версию (с
большим номером), в которую вернули предыдущее содержимое или исправление.
Старый выпуск из консоли никуда не девается (пока не удалён вручную) и
может быть переиспакован под новым номером версии.

## 5. Выключатели

Три независимых уровня — от «весь сервер» до «одна машина»:

| Уровень | Где | Действие |
|---|---|---|
| Сервер целиком | `UPDATES_DISABLED=true` (переменная окружения) | Жёсткий выключатель: `/updates/:channel/latest.yml` и `/:channel/:file` всегда отвечают так, будто обновлений нет. Консоль (политика) это **не** переопределяет — годится, чтобы быстро остановить раздачу, не трогая настройки в базе. |
| Политика раздачи | `update_policy.enabled = false` (консоль, `PUT /api/admin/updates/policy`) | Мягкий выключатель на уровне сервера: `policy.json` отдаёт `enabled:false`, клиенты не проверяют обновления, но сама раздача (проценты, target) сохраняется в настройках на будущее. |
| Одна машина (или группа машин) | `UpdatesEnabled` = `0` (`REG_DWORD`) в `HKLM\SOFTWARE\Policies\OpenMyChat Enterprise` | Ставится через `configure-client.ps1 -DisableUpdates` (вернуть — `-EnableUpdates`) или групповой политикой (раздел 1, пункт 4). Годится для машины с особой ролью (например, стенд с конкретной версией для теста), которую не должна трогать общая раздача. |

## 6. Диагностика: коды ошибок парка

Вкладка «Обновления» → «Парк» в консоли показывает `fleet.errors` — сколько
машин видело каждый код последней ошибки (клиент присылает его заголовком
`X-MyChat-Update-Error` при следующей проверке). Коды и что с ними делать:

| Код | Что значит | Что делать |
|---|---|---|
| `signature-untrusted` | `Get-AuthenticodeSignature` вернул не `Valid` — подпись повреждена или сертификат не заверен цепочкой доверия | Обычно означает, что на машине не установлен корневой сертификат Centras (см. раздел 1, пункт 2) — раздать `установить-сертификат.ps1`/`.bat`. Если сертификат стоит, а ошибка не проходит — проверить, не истёк ли сертификат подписи. |
| `signature-foreign` | Отпечаток сертификата в подписи файла не совпадает с закреплённым (`0EB61614FC390FCD11BDF8DBFD40BE62EE10862A`) | Файл подписан не тем сертификатом. Если это не смена ключа подписи (тогда нужно менять закреплённый отпечаток в коде клиента и переиздавать его), считать компрометацией канала раздачи и разбираться, откуда файл. |
| `version-mismatch` | `ProductVersion` в файле не совпадает с версией из `latest.yml` или не больше текущей установленной | Обычно рассинхронизация сборки: `latest.yml` и `Setup.exe` из разных сборок. Пересобрать и переиздать выпуск целиком через `publish-update.ps1`. |
| `signature-unreadable` | PowerShell-проверка подписи вернула не тот JSON, что ожидался, либо вообще не отработала | Часто — Smart App Control/антивирус заблокировал запуск PowerShell на клиенте, либо тайм-аут (30 с). Проверить локально на одной машине, прежде чем считать проблемой выпуска. |
| `sha512` | sha512 скачанного файла не совпал со значением в `latest.yml` | Либо сеть повредила файл при докачке (редко — electron-updater сам перескачивает), либо `latest.yml` был подготовлен не той же сборкой, что `Setup.exe`. Переиздать выпуск. |
| `network` | Не удалось получить `policy.json`/`latest.yml`/файл — таймаут, DNS, обрыв TLS | Обычно временная проблема сети или сертификата (раздел 1, пункт 1). Если массово — проверить, не упал ли сервер обновлений или прокси. |
| `http-5xx` | Сервер ответил 5xx на запрос обновления | Смотреть журнал сервера в это время: неполадка на сервере обновлений, а не у клиента. |
| `build-misconfigured` | В собранном `app-update.yml` нет `publisherName` — клиент отказывается проверять подпись вообще, лишь бы не пропустить непроверенный файл | Это ошибка сборки, а не раздачи: проверить `build.win.signtoolOptions.publisherName` в `desktop/package.json` и пересобрать. `publish-update.ps1` должен был отказать ещё на этапе публикации — если выпуск всё же попал на сервер таким, откатывать (см. раздел 4) и переиздавать. |

Полезно помнить: маршрут `GET /updates/:channel/latest.yml` ограничен 120
запросами в минуту с одного IP. Для небольшого офиса это с запасом, но за
одним NAT крупного филиала может сидеть достаточно рабочих мест, чтобы
регулярно упираться в предел (клиенты получат `429` и попробуют снова по
своему расписанию — ничего не сломается, но в мониторинге это будет видно
как всплеск ошибок). Если это ваш случай, подстройте `checkIntervalMinutes`
пошире, чтобы разрежать поток проверок.

## 7. Первичный переход парка с версии 1.0.0

Компьютеры, на которых установлена версия до появления автообновления
(1.0.0), не умеют ни проверять `/updates/*`, ни принимать IPC про
обновления — интерфейс на них может показать только баннер «Установите
новую версию» со ссылкой на `setupUrl` из `/updates/policy.json` (логика —
`legacyShell` в `lib/update-status.mjs`: есть `window.electronAPI`, но нет
`getUpdateState`). Автоматически они не обновятся ни разу — этот переход
разовый и делается вручную.

**Когда старая оболочка видит баннер.** Интерфейс спрашивает
`policy.json` от имени версии `1.0.0` (заголовки
`X-MyChat-Client-Version: 1.0.0`, `X-MyChat-Install-Kind: copy`), но без
`installId` — такой клиент всегда попадает в последнюю корзину раздачи.
Поэтому ссылку (и баннер) версия 1.0.0 получает, **только если**:

- `minVersion` в политике больше `1.0.0` (например, `1.1.0`) — тогда
  обновление для неё обязательное: баннер «Обязательное обновление…», без
  кнопки «скрыть»; **или**
- `rolloutPercent` канала `stable` равен `100`. Необязательный баннер
  сотрудник может скрыть — до перезапуска приложения.

При `UPDATES_DISABLED=true`, выключенной политике или без выпуска баннера
нет вовсе.

1. Опубликовать первый выпуск с автообновлением как обычно (раздел 2) и
   поднять `minVersion` до `1.1.0` (или раздачу до 100 %), чтобы старые
   оболочки получили ссылку.
2. Разослать сотрудникам с версией 1.0.0 ссылку на `Setup.exe` (баннер её
   уже показывает, но не помешает продублировать письмом/в общем чате) или
   раздать установщик так же, как раньше — через `install.bat`/сетевую
   папку.
3. После того как сотрудник один раз вручную поставит версию с
   автообновлением, дальше его компьютер обновляется уже сам по политике
   раздачи — второй раз вручную ничего разносить не нужно.
