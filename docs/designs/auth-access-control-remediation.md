# Design: OpenMyChat Auth & Access-Control Remediation

## Problem Statement
OpenMyChat Enterprise (self-hosted corporate chat for Сентрас Иншуранс, `server/` + `desktop/`) shipped a "pure production" refactor on 2026-09-07 that removed Kanban/BBS and mock data, but never audited the auth/access-control surface. The server binds `0.0.0.0:2004` and is documented as LAN/WAN reachable, with real employee accounts already provisioned in the live DB. Two independent reviews (a code audit, then an independent Claude subagent with no access to the first review's conclusions) each found unauthenticated or under-authorized routes that let any network-reachable party impersonate any employee, including admin, and let any authenticated employee read/write any channel or reset any account's password without knowing the old one.

## Evidence (this is present-tense risk, not hypothetical)
- **The desktop client has no working password-login path at all today.** `desktop/src/renderer/src/App.jsx:192-253` runs `performInstantLogin()` unconditionally on every launch, which tries `/api/auth/knock` then falls back to `/api/auth/instant-login`. `AccountSwitcherModal.jsx` (built entirely on `/api/auth/profiles` + instant-login, actual UI text per [AccountSwitcherModal.jsx:45](desktop/src/renderer/src/components/AccountSwitcherModal.jsx#L45): "Выберите коллегу для мгновенного входа без пароля" — "pick a colleague for instant passwordless login", paraphrased above) is the only account picker actually rendered. `LoginView.jsx` (real username/password form) exists in the tree but is never imported or rendered — dead code. **This means the Ordered Fix List below cannot simply delete the server-side instant-login/profiles endpoints — that would lock every employee out of the app.** The server fix is real and necessary, but it is gated on shipping a working login screen in `desktop/` first.
- Worse, when `performInstantLogin(null)` falls through with no identifier, `AuthService.instantLogin` defaults to "Tamerlan (uin 1436) or first active user" ([server/src/services/auth.service.js:132-141](server/src/services/auth.service.js#L132)) — a **brand-new, unpaired install auto-logs the operator into a specific named real employee's account by default, with no prompt at all.**
- `POST /api/auth/instant-login` ([server/src/api/index.js:110](server/src/api/index.js#L110)) and `GET /api/auth/profiles` ([:120](server/src/api/index.js#L120)) together let anyone enumerate every username and mint a valid token for any of them, including admin, with zero password check and no auth guard on the routes themselves.
- `POST /api/auth/register` ([server/src/api/index.js:100](server/src/api/index.js#L100) → [auth.service.js:67-100](server/src/services/auth.service.js#L67)) is completely unauthenticated and never reads the seeded `allow_registration` setting ([db/index.js:466](server/src/db/index.js#L466)) — anyone who can reach the server can self-provision a fully valid employee account with zero invite or approval, same bug class as instant-login.
- All seeded real employee accounts — not just admin — share the password `123456` ([server/src/db/index.js:318](server/src/db/index.js#L318), [:405-410](server/src/db/index.js#L405-L410)); the server's own boot banner prints the wrong password (`admin123`) for admin, actively misleading anyone auditing it.
- `MessageService.getMessages`/`sendMessage`/`searchMessages` never check `channel_members` for `conversationType==='channel'` ([server/src/services/message.service.js:59-68,97-118,168-182](server/src/services/message.service.js#L59)) — reachable today via the admin-created public channels and via direct message/channel IDs guessed by any authenticated employee (see note in Approaches Considered on the exact reachability). Direct messages are correctly scoped — this gap is channel-specific.
- `GET /files/recent` ([api/index.js:758](server/src/api/index.js#L758), `requireAuth` only) lists the 50 most-recently uploaded files server-wide, including ones shared in private channels/DMs, with no membership scoping.
- `changePassword` only checks `oldPassword` if the caller supplies it ([server/src/services/user.service.js:84-97](server/src/services/user.service.js#L84-L97)) — any live bearer token can silently take over the account by omitting it.
- A second unauthenticated token-minting path, `POST /api/auth/knock` ([server/src/services/device.service.js:10-120](server/src/services/device.service.js#L10-L120)), has three distinct branches: (a) a device already paired via prior admin `bindDevice` gets a silent token reissue — this is the intended "remembered device" reconnect UX and is not itself a bug; (b) an unrecognized device is queued with no token — also fine as-is; (c) **the caller's source IP matching a user's `bound_ip` auto-issues a live token with no prior admin action at all** — risky on a WAN box behind shared corporate NAT, this is the one branch that needs closing.
- The WebSocket gateway ([server/src/ws/server.js](server/src/ws/server.js)) has no equivalent to the REST `requireAuth`/`requireAdmin` middleware: `auth` never rechecks `is_active` (a deactivated employee keeps realtime access for up to 7 days on their existing token), `rd_request` never checks the `can_remote_control` permission the DB schema already models, and the relay handlers (`rd_webrtc_offer/answer`, `rd_ice_candidate`, `rd_input_event`, `rd_end` — [ws/server.js:267-277](server/src/ws/server.js#L267)) forward on a client-supplied `sessionId` with no check that `RemoteDesktopService` actually has that session in `ACCEPTED` status.
- `GET /files/download/:id` ([:748](server/src/api/index.js#L748)) has zero middleware — no auth at all — and `GET /admin/db/backups/:filename` ([:826](server/src/api/index.js#L826)) has no path-sanitization.
- **"Контурный администратор" (scoped admin) is decorative in three places.** `DeviceService.getPendingDevices`/`bindDevice` ([device.service.js:125-213](server/src/services/device.service.js#L125)) never filter by department, so a scoped admin sees and binds devices company-wide; `OrgParserService.applyImport` ([org-parser.service.js:287](server/src/services/org-parser.service.js#L287)) accepts `adminScopeDeptId` but never reads it. This contradicts the role's own DB description ("manage only their own employees and departments") and is the same bug class as the rest of this list — `UserService.getAllUsers`/`OrgService.getOrganizationTree` already implement the correct department-filter pattern to copy. Files have no FK to the conversation they were shared in (only `uploader_id` plus a free-form `metadata_json` on the message) — a real fix has to resolve conversation membership through that metadata, not just check `uploader_id === req.user.id`.
- No `.gitignore` anywhere — `server/data/mychat.db` (real password hashes, chat history), `node_modules`, and compiled `.exe` releases are all untracked and one `git add .` away from entering history.
- `antiflood_limit`, `bad_words_enabled/list`, and `ip_blacklist` are stored and shown in the admin UI but enforced nowhere in the code — decorative controls that give a false sense of protection.
- `JWT_SECRET` has no production delivery mechanism: `server/package.json` has no `dotenv`, and `installer/install-service.bat:35` registers the Windows Service via bare `sc create ... binPath= "\"%NODE_PATH%\" \"%SERVER_JS%\""` with no env-var injection anywhere. Making the secret mandatory without also fixing this breaks the live service on next restart.

## Status Quo (cost of doing nothing)
Any device that can reach port 2004 — inside the corporate LAN, or over WAN per the project's own deployment docs — can already impersonate any employee including admin, read every private channel, exfiltrate every uploaded file, and run arbitrary SQL via the admin DB console, with zero credentials and zero rate-limiting to slow the attempt down. This is live against a database seeded with real employee identities.

## Scope & Users Affected
All ~10+ named employees of Сентрас Иншуранс already provisioned in `mychat.db`, plus the SuperAdmin account. No new users need onboarding — this is a fix to an already-deployed system with an active user base, not a pre-launch hardening pass.

## Constraints
- No new deployable artifact or distribution channel — ships through the existing Windows Service / electron-builder pipeline.
- Must not break the live realtime path (WS reconnect, multi-device sessions) — WS auth changes need care, not just REST-style middleware copy-paste.
- Fixing the code does not retroactively fix the `123456` password already sitting in the live DB — that needs a one-time operational action (forced reset), tracked as a separate dependency, not assumed away by the code fix.
- **The server-side instant-login/profiles fix is hard-blocked on desktop client work.** `LoginView.jsx` (real password form) is dead code today — closing the server endpoints before wiring up a real login screen and retiring `AccountSwitcherModal`'s passwordless picker would lock out every employee. This changes the effort estimate for Approach B below: it is not server-only.
- `JWT_SECRET` cannot simply become "fail if unset" without also updating `installer/install-service.bat` (and `installer/setup-mychat.ps1`) to generate and persist a secret at install time — the current service registration has no env-var injection path.

## Premises
1. The instant-login/profiles-list gap is a live, exploitable auth bypass, not theoretical — the server is already network-reachable with real accounts provisioned. **Agreed.**
2. Doing nothing costs real, present-tense exposure (impersonation, data exfiltration), not speculative risk. **Agreed.**
3. *(revised, narrowed after doc review)* The `requireAuth`/`requireAdmin` pattern is applied consistently on REST, but the WebSocket gateway has no equivalent — this plan commits to closing the `is_active` recheck and the `send_message` membership-check with a small amount of new code. It does **not** commit to `rd_request` permission-gating in this pass — that needs a product decision first (see Open Questions) and is tracked as deferred, not silently included.
4. *(revised)* The code fix ships through the existing deploy pipeline with no new artifact, but the `123456` password already in the live DB requires a separate operational step (forced reset), independent of any code deploy.

## Cross-Model Perspective
An independent Claude subagent (no access to this session, read the code fresh) confirmed the instant-login/profiles-list pair as the highest-leverage fix, then surfaced findings the first pass missed: the channel-membership IDOR, the shared `123456` password across all real accounts (not just admin), the WS `is_active`/`can_remote_control` gaps, the `changePassword` silent-takeover bug, the second `/auth/knock` bypass path, and path-traversal risk on the backup-download route. It also flagged that no injection risk exists in the parameterized services — the only raw-SQL surface (`executeCustomSql`) is an intentional admin feature, not a bug, and the correct mitigation is making admin compromise hard rather than removing the console. Its one-day ordered fix list became the basis for Approach B below.

**Correction from the spec-review pass:** the subagent's specific framing of the channel IDOR — "any authenticated user can create a channel of any type, including private" — does not hold: `POST /channels` calls `MessageService.createChannel`, which does not exist anywhere in the codebase; that route 400s on every real call today. The only working creation path is the admin-only `POST /admin/channels`, which hardcodes `type: 'public'`. The underlying bug (no membership check in `getMessages`/`sendMessage`/`searchMessages`) is still real and still reachable — any authenticated employee who knows or guesses a valid channel ID from the admin-created set can read/write it without being a member — it's just not a "self-service private channel" exploit as originally worded.

## Approaches Considered
### Approach A: Minimal viable — stop the bleeding
Only the zero-new-infra fixes that kill the "free" admin-takeover path: remove/gate `instant-login`+`profiles`+the risky `knock` branch, mandatory `JWT_SECRET`, mandatory `oldPassword`, auth-gate file download, sanitize backup filename, fix the misleading banner, `.gitignore`. Effort S, Risk Low. **Rejected** — leaves the channel membership gap (any employee reads/writes any channel they know the ID of) and the WS `is_active` gap open; both are exploitable by an already-authenticated insider, which is a realistic threat here. It also, as originally scoped, ignored that the desktop client has no working alternative to instant-login — see Approach B's revised scope below, which applies to A too.

### Approach C: Systemic fix via shared `authz.js`
One shared authorization module (`assertChannelMember`, `assertActive`, `assertPermission`) used by both REST and WS, plus collapsing `instant-login`/`knock` into an explicit `DEV_AUTH_BYPASS` env flag instead of deleting them outright. Effort M-L, Risk Med. **Rejected for this pass** — more design work up front for a security fix that needs to ship now; worth reconsidering as a follow-up refactor once the concrete holes are closed, not as the vehicle for closing them.

## Recommended Approach
**Approach B — Full remediation.** This is a live breach in a system with a real, already-provisioned user base — the "boil the ocean" call here is literal, not aspirational: a half-fix (A) leaves the channel-IDOR and shared-password findings, which are the two most severe items from the independent review, unaddressed.

## Ordered Fix List
1. `.gitignore` for `data/`, `node_modules/`, `dist/`, `*.exe` — independent of everything else, do first.
2. **`desktop/`: wire up `LoginView.jsx` as the real entry point.** On launch: attempt a silent reissue only via the paired-device `knock` branch (kept, legitimate reconnect); if that fails or no device is paired, render `LoginView` and require username+password — never fall through to instant-login or the no-identifier default-employee fallback (both removed). Retire `AccountSwitcherModal`'s passwordless picker entirely. **Hard prerequisite for item 3** — do not ship item 3 first.
3. Remove `POST /api/auth/instant-login` and `GET /api/auth/profiles`; gate `POST /api/auth/register` behind the `allow_registration` setting it currently ignores (or remove it too, if self-registration isn't wanted); disable the IP-auto-match branch of `POST /api/auth/knock` (keep the paired-device reissue and unknown-device-queue branches — they're legitimate).
4. `JWT_SECRET`: make it mandatory in `config/index.js`, **and** update `installer/install-service.bat`/`installer/setup-mychat.ps1` to generate a secret at install time and persist it where the service registration can read it. Ship these together — mandatory-without-delivery breaks the live service on next restart.
5. WS `auth` handler: recheck `is_active` on every bind, not just at REST login.
6. Channel-membership check in `MessageService.getMessages`/`sendMessage`/`searchMessages`, enforced at all call sites (REST + WS `send_message`). Once `createChannel` is implemented/fixed (see Approaches Considered correction), also validate the `type` field server-side rather than trusting the client.
7. `changePassword`: make `oldPassword` mandatory, not conditional.
8. `requireAuth` + conversation-membership check (resolved via a `json_extract`/`LIKE` scan over the message's `metadata_json` back-reference, not `uploader_id` — unindexed, acceptable at this app's ~10-employee scale) on `GET /files/download/:id`; apply the same membership scoping to `GET /files/recent`.
9. `path.basename()` the filename in `GET /admin/db/backups/:filename`.
10. Add a `must_change_password` column (schema migration) and set it on all seeded/default accounts. Enforce server-side, not just client redirect: every `requireAuth` route rejects until cleared, except an explicit allowlist (`/users/password`, `/auth/me`, `/auth/login`) so the user can actually reach the change-password flow.
11. Minimal in-memory rate limit on `POST /auth/login` and WS `auth` (no new dependency).
12. Fix the misleading `admin123` banner text.
13. WS remote-desktop relay handlers (`rd_webrtc_offer/answer`, `rd_ice_candidate`, `rd_input_event`, `rd_end`) must verify `RemoteDesktopService` has the given `sessionId` in `ACCEPTED` status before forwarding — currently any client-supplied session ID is relayed.
14. Make `DeviceService.getPendingDevices`/`bindDevice` and `OrgParserService.applyImport` actually respect `adminScopeDeptId`, mirroring the department-filter pattern already correct in `UserService.getAllUsers`/`OrgService.getOrganizationTree` — closes the decorative scoped-admin boundary.

## Open Questions
- `rd_request` currently has no `can_remote_control` enforcement — closing it changes who is allowed to request remote-desktop assistance today. Needs a product decision (who should be allowed to initiate RD?), not just a code patch — flagged for the Eng review, not silently bundled into the fix list above.
- CORS is currently `origin: true, credentials: true`. Locking it down needs the actual Origin values the Electron client sends in practice, to avoid breaking legitimate clients blind — deferred pending that data.
- TLS/HTTPS termination is real infrastructure work (reverse proxy + certs), out of scope for a code-only pass — flagged as the next priority after this remediation.
- Decorative `antiflood`/`bad_words`/`ip_blacklist` settings: wire them up for real, or remove them from the admin UI so it stops implying protection that doesn't exist? Product call, not an engineering default.

## Success Criteria
- Every item in the Ordered Fix List is independently verifiable by request/response, e.g.: `instant-login`/`profiles` post-fix return 404/410; `register` without `allow_registration` returns 403; a non-member GET on a channel returns 403; WS `auth` on a deactivated user's token is rejected; a forged `rd_input_event` with an unaccepted `sessionId` is dropped; the service restarts cleanly after the `JWT_SECRET` change with no manual intervention.
- A real employee can complete a full login → chat → logout cycle through the desktop client using item 2's new login screen, with no instant-login/knock dependency.
- All real employee accounts have been force-rotated off `123456` and the login banner reports the true admin credential state.
- No behavior regression in the live realtime path (reconnect, multi-device, remote-desktop consent flow) — verified manually against the desktop client, not just unit-level.

## Dependencies
- Item 3 (removing instant-login/profiles) is blocked on item 2 (working desktop login) shipping first — sequencing, not just scope, matters here.
- Item 10 (password rotation) needs sign-off from whoever owns the live `mychat.db` before forcing resets on real employee accounts — this touches people who are actively using the app today.
- The `rd_request` open question blocks on a product decision about who may request remote-desktop sessions.

## The Assignment
Before writing any code: get explicit sign-off from whoever owns the live server that a forced password reset (item 10) is acceptable to push to real, currently-active employee accounts — that's the one item in this list with a real-world blast radius beyond the codebase, and it should not ship silently inside a routine "security patch" commit. Second: confirm the item 2 → item 3 sequencing (desktop login screen before server-side removal) is understood by whoever implements this, since shipping item 3 alone would lock out every employee.
