## Как читать план

- **Этапы идут по срочности.** Этап 0 делается в панели Railway без изменения кода. Этапы 1–2 — код, их можно вести параллельно. Этапы 3–4 — организационные.
- **У каждой задачи:** что сломано, что менять, как проверить готовность, что нужно для выкладки.
- **Выкладка:**
  - «Сервер» — достаточно выкладки на Railway; интерфейс тоже обновится, он приходит с сервера.
  - «Клиент» — изменён главный процесс Electron, нужна пересборка и переустановка приложения у сотрудников.
- **Оценка** — рабочие дни одного разработчика, включая тесты.
- **Проверка:** каждая исправленная уязвимость закрывается автотестом, который воспроизводит атаку и падал до исправления. Без такого теста задача не считается сделанной.

## Этап 0. Срочные настройки (сегодня, без кода)

### 0.1. Постоянный диск для данных
- **Проблема:** переписка, вложения, резервные копии и ключ подписи токенов лежат на диске контейнера и стираются при каждом перезапуске.
- **Сделать:** в Railway у сервиса открыть Volumes, подключить диск на `/app/server/data`.
- **Готово, когда:** сообщение и файл, отправленные до перезапуска сервиса, видны после него.

### 0.2. Секреты в переменных окружения
- **Проблема:** без `JWT_SECRET` ключ генерируется заново после очистки диска, и всех выкидывает; без `INITIAL_ADMIN_PASSWORD` учётная запись `admin` создаётся с паролем `123456`.
- **Сделать:** задать `JWT_SECRET` (не короче 32 случайных байт, например `openssl rand -base64 48`) и `INITIAL_ADMIN_PASSWORD` (длинный случайный, хранить в менеджере паролей).
- **Готово, когда:** обе переменные заданы; после перезапуска сотрудники остаются в системе.

### 0.3. Пароли по умолчанию
- **Проблема:** по рабочим журналам у живых учётных записей был общий пароль `123456`, смена «ждала согласования».
- **Сделать:** проверить `admin` и все учётные записи, созданные импортом; всем, у кого пароль не менялся, выставить принудительную смену при входе.
- **Готово, когда:** вход с `123456` не проходит ни для одной учётной записи.

### 0.4. Ограничение по адресам
- **Проблема:** сервис доступен из всего интернета; проверка «только из приложения» подделывается одним заголовком.
- **Сделать:** заполнить `ALLOWED_CLIENT_IPS` внешними адресами офисов и VPN; проверить `TRUSTED_PROXY_IPS`.
- **Готово, когда:** с адреса вне списка сервер отвечает отказом и на страницу, и на `/api`, и на `/ws`.

### 0.5. Регион хранения
- **Проблема:** персональные данные сотрудников, вероятно, хранятся вне Казахстана (закон РК № 94-V о персональных данных).
- **Сделать:** посмотреть регион сервиса и базы в Railway; передать вопрос юристу. Решение — на этапе 4.1.

## Этап 1. Сервер: доступ и сессии (неделя 1, выкладка сервера)

### 1.1. Вход по устройству — только с секретом
- **Проблема:** зная номер привязанного устройства, можно без пароля получить токен сотрудника на 7 дней, даже после смены им пароля. Номер виден администраторам и создаётся через `Math.random`.
- **Сделать:**
  1. При привязке сервер выдаёт устройству случайный секрет (32 байта из `crypto.randomBytes`), в базе хранит только его хеш.
  2. Выдача токена по устройству — только при предъявлении секрета, сравнение за постоянное время.
  3. Номер устройства и секрет не показывать в консоли, API и рассылках администраторам.
  4. Смена пароля и отключение учётной записи снимают привязку всех устройств.
  5. Ограничение частоты запросов и запись каждой выдачи токена в журнал аудита.
- **Файлы:** `server/src/services/device.service.js`, `server/src/api/index.js` (`/auth/knock`, `/admin/devices/*`), `desktop/src/renderer/src/App.jsx` (хранение секрета).
- **Миграция:** существующие привязки становятся недействительными; сотрудники один раз входят по паролю.
- **Тесты:** по номеру без секрета токен не выдаётся; после смены пароля старый секрет не работает; ответы администраторских маршрутов не содержат секретов.
- **Оценка:** 1,5 дня.

### 1.2. Администратор отдела не управляет администраторами
- **Проблема:** проверка зоны смотрит только отдел сотрудника. Администратор отдела может сбросить пароль главному администратору, привязать себе его устройство и получить его токен, понизить или отключить его.
- **Сделать:**
  1. В `assertWithinAdminScope` отказывать, если у цели роль с `is_admin` или `is_scoped_admin`, а действующий не главный администратор.
  2. Привязка устройства никогда не возвращает токен администратору.
  3. Проверка зоны для `/admin/devices/unbind`.
  4. `GET /users/:id` для администратора отдела — только по своей зоне и без служебных полей (`last_login_ip`, `bound_ip`, `token_version`).
- **Файлы:** `server/src/api/index.js`, `server/src/services/device.service.js`, `server/src/services/user.service.js`.
- **Тесты:** администратор отдела получает 403 на сброс пароля, изменение, отключение и привязку устройства главного администратора.
- **Оценка:** 1 день.

### 1.3. Нет пароля администратора по умолчанию
- **Проблема:** без `INITIAL_ADMIN_PASSWORD` создаётся `admin` / `123456`; стартовое сообщение это подсказывает.
- **Сделать:**
  1. В рабочем режиме (`NODE_ENV=production` или на Railway) без `INITIAL_ADMIN_PASSWORD` сервер не стартует и пишет понятную причину.
  2. В разработке — случайный пароль, показанный один раз в консоли.
  3. Пароль из переменной проходит ту же политику, что и обычные.
  4. Убрать подсказку пароля из стартового сообщения.
  5. `ADMIN_PASSWORD_RESET` выставляет принудительную смену пароля; отметку о применении хранить как HMAC на ключе сервера, не отдавать в `GET /admin/settings`.
- **Файлы:** `server/src/db/identity/index.js`, `server/src/index.js`, `server/src/config/index.js`.
- **Тесты:** запуск без переменной в рабочем режиме завершается ошибкой; слабый пароль из переменной отклоняется.
- **Оценка:** 0,5 дня.

### 1.4. Отзыв открытых соединений
- **Проблема:** после смены пароля, блокировки или понижения роли уже открытое WebSocket-соединение продолжает писать, звонить и запрашивать удалённый стол.
- **Сделать:**
  1. `disconnectUser` (через `terminate`) при смене пароля (кроме соединения, из которого сменили), смене роли, отключении учётной записи.
  2. Раз в 60 секунд перепроверять сессию каждого соединения (`resolveSession`: активность, одобрение, версия токена) и закрывать недействительные.
  3. Перед чувствительными действиями (`rd_request`, `call_offer`) проверять права по свежим данным, а не по снимку при входе.
- **Файлы:** `server/src/ws/server.js`, `server/src/api/index.js`.
- **Тесты:** после смены пароля и после отключения старое соединение закрывается в течение секунды; пониженный администратор не может запросить удалённый стол.
- **Оценка:** 1 день.

### 1.5. Лимиты WebSocket
- **Проблема:** до входа принимаются сообщения до 16 МБ и разбираются как JSON; нет ограничения частоты; одна учётная запись может засыпать всех рассылкой статусов и звонками.
- **Сделать:**
  1. До входа — только сообщение `auth` не больше 4 КБ; любое другое закрывает соединение.
  2. Ограничение числа соединений на IP и на пользователя.
  3. Счётчик частоты на соединение по типам: статус 1/с, «печатает» 2/с, сообщения 5/с, звонок и запрос удалённого стола — 1 раз в 10 секунд на одного адресата.
  4. Не писать в базу и не рассылать, если статус не изменился.
  5. Файлы удалённого стола передавать частями и снизить общий предел сообщения.
  6. Входящий звонок не пробивает «Не беспокоить».
- **Файлы:** `server/src/ws/server.js`.
- **Тесты:** большое сообщение до входа закрывает соединение; превышение частоты отбрасывается; повторная смена одного статуса не даёт рассылки.
- **Оценка:** 1 день.

### 1.6. Загрузка файлов без переполнения памяти
- **Проблема:** файл целиком держится в памяти, хеш и запись синхронные; 20 параллельных загрузок по 100 МБ займут около 2 ГБ.
- **Сделать:** `multer.diskStorage` во временную папку или потоковая запись с хешем на лету; не больше 2 одновременных загрузок на пользователя; учитывать настройку `max_upload_size_mb`; обновить `multer` до ветки 2.x.
- **Файлы:** `server/src/api/index.js`, `server/src/services/file.service.js`, `server/package.json`.
- **Тесты:** третья одновременная загрузка получает отказ; потребление памяти при загрузке 100 МБ не растёт на 100 МБ.
- **Оценка:** 0,5 дня.

### 1.7. Защита входа от подбора
- **Проблема:** сообщение о блокировке отличается от «неверный логин или пароль» и выдаёт существующие логины; любого, включая `admin`, можно держать заблокированным; перебор по многим логинам с одного IP не ограничен.
- **Сделать:** одинаковый ответ при блокировке; лимит неудачных входов на IP независимо от логина; нарастающая задержка вместо жёсткой блокировки; запись неудачных входов и блокировок в журнал аудита; корректный разбор IPv6 в `normalizeIp` через `net.isIP`.
- **Файлы:** `server/src/services/auth.service.js`, `server/src/services/rate-limiter.js`, `server/src/services/ip-access.service.js`.
- **Тесты:** ответы для несуществующего и заблокированного логина совпадают; 50 логинов подряд с одного IP упираются в лимит.
- **Оценка:** 1 день.

### 1.8. Подмена данных в запросах
- **Проблема:** в оповещении автор берётся из тела запроса и перекрывает настоящего; тип сообщения и адресат не проверяются; сотрудник сам меняет себе имя и должность.
- **Сделать:**
  1. Оповещения: явный список разрешённых полей, `author_id` всегда из сессии.
  2. Сообщения: белый список `conversationType` и `msgType`, адресат — существующий активный пользователь, `reply_to_id` — из той же переписки; «печатает» только существующему адресату.
  3. Имя и должность меняет только администратор.
  4. Отметка ознакомления — только для существующего оповещения, адресованного сотруднику; без текста ошибок базы в ответе.
- **Файлы:** `server/src/api/index.js`, `server/src/ws/server.js`, `server/src/services/message.service.js`, `server/src/services/user.service.js`, `server/src/services/announcement.service.js`.
- **Тесты:** оповещение с чужим `author_id` сохраняется от имени отправителя; сообщение типа `system` отклоняется.
- **Оценка:** 1 день.

### 1.9. Консоль SQL
- **Проблема:** запрет `ATTACH` обходится комментарием, из соседней базы читаются хеши паролей; `VACUUM INTO` пишет файлы в любое место.
- **Сделать:** консоль работает через отдельное подключение только для чтения (`readOnly: true`); запрещённые операции блокируются на уровне SQLite, а не регулярным выражением; изменения данных — только через отдельные проверенные действия; после миграции удалить старые `identity.db` и `pre-identity-split.db`.
- **Файлы:** `server/src/services/db-studio.service.js`.
- **Тесты:** `/**/ ATTACH`, `VACUUM INTO`, `PRAGMA` с записью отклоняются.
- **Оценка:** 0,5 дня.

## Этап 2. Клиент: удалённый стол и сборка (недели 1–2, переустановка приложения)

Общий принцип: интерфейс приходит с сервера, поэтому главный процесс не должен доверять странице ни в чём, что касается экрана, ввода, буфера обмена и файлов.

### 2.1. Разрешения только на микрофон
- **Проблема:** разрешение `media` выдаётся без проверки, что именно запрашивается; страница может снять экран старым способом (`chromeMediaSource: 'desktop'`) или включить микрофон без сеанса.
- **Сделать:** разрешать `media`, только если `details.mediaTypes` — ровно `['audio']`; проверка разрешений без пустого источника; удалить обработчик `get-desktop-sources` (интерфейс его не вызывает) или пускать только при активном сеансе.
- **Файлы:** `desktop/src/main/main.js`.
- **Проверка:** в сборке для разработки запрос видео через `getUserMedia` отклоняется, звонки работают.
- **Оценка:** 0,5 дня.

### 2.2. Согласие на удалённый стол — в главном процессе
- **Проблема:** главный процесс верит странице, какой доступ выдан; окно согласия есть только в интерфейсе с сервера; красная полоса видна только при свёрнутом окне.
- **Сделать:**
  1. На `rd-session-start` главный процесс сам показывает системное окно: кто подключается и с каким доступом; сеанс создаётся только после ответа в этом окне.
  2. Уровень доступа берётся из ответа сотрудника в системном окне, а не из данных страницы.
  3. Красная полоса поверх всех окон на всё время сеанса.
  4. Настройка политики, запрещающая полный доступ на конкретном ПК.
- **Файлы:** `desktop/src/main/main.js`, `desktop/src/main/host-session.js`, `RemoteDesktopHostModal.jsx`.
- **Оценка:** 1,5 дня.

### 2.3. Буфер обмена и снимки экрана только в сеансе
- **Проблема:** чтение буфера и миниатюры экранов доступны странице в любой момент.
- **Сделать:** `rd-clipboard-read` — только при активном сеансе с полным доступом и согласием на буфер, отметка согласия хранится в главном процессе; `rd-list-screens` — только при активном сеансе; оба — только из главного окна.
- **Файлы:** `desktop/src/main/main.js`.
- **Оценка:** 0,5 дня.

### 2.4. Буфер оператора и уровень доступа по умолчанию
- **Проблема:** сотрудник может сам включить передачу буфера администратора себе; в окне согласия по умолчанию выбран полный доступ; администратор отдела может запрашивать удалённый стол у любого сотрудника; запросы не истекают.
- **Сделать:**
  1. Сервер пересылает `rd_clipboard_mode` от сотрудника только в ответ на запрос оператора и только при полном доступе; окно оператора включает буфер только из состояния «ожидает ответа».
  2. По умолчанию «Только просмотр».
  3. Администратор отдела — только в своей зоне; один ожидающий запрос на пару; запрос истекает через 60 секунд; максимальная длительность сеанса.
  4. Сеанс закрывается, если отключилось устройство сотрудника, на котором он идёт.
- **Файлы:** `server/src/ws/server.js`, `server/src/services/remote-desktop.service.js`, `RemoteDesktopViewer.jsx`, `RemoteDesktopHostModal.jsx`.
- **Тесты (сервер):** включение буфера со стороны сотрудника не пересылается; запрос вне зоны отклоняется; ожидающий запрос истекает.
- **Оценка:** 1 день.

### 2.5. Принятые файлы
- **Проблема:** файлы любого типа, включая `.exe`, `.lnk`, `.hta`, сохраняются молча и без пометки «из интернета», SmartScreen их не проверит.
- **Сделать:** спрашивать сотрудника перед сохранением; записывать поток `Zone.Identifier` с `ZoneId=3`; исполняемые типы блокировать или сохранять с безопасным расширением; обрабатывать зарезервированные имена Windows; в журнал — размер и хеш, посчитанные сервером.
- **Файлы:** `desktop/src/main/main.js`, `server/src/ws/server.js`.
- **Оценка:** 0,5 дня.

### 2.6. Адрес сервера
- **Проблема:** в клиенте можно указать `http://` и любой адрес; переменные окружения переопределяют адрес в рабочей сборке; LAN-пресеты по `http`.
- **Сделать:** в рабочей сборке — только `https` и `wss`, `http` только для `localhost` в разработке; `VITE_DEV_SERVER_URL` и `MYCHAT_SERVER_URL` игнорировать при `app.isPackaged`; заменить пресеты на `https`.
- **Файлы:** `desktop/src/main/main.js`, `ServerConnectModal.jsx`, `LoginView.jsx`, `App.jsx`.
- **Оценка:** 0,5 дня.

### 2.7. Каналы связи с главным процессом
- **Проблема:** часть обработчиков не проверяет отправителя (`get-device-info` отдаёт имя компьютера и пользователя, `show-notification` позволяет показать поддельное системное уведомление); нет обработчика `will-redirect`; мёртвое окно уведомлений с доступом к Node.
- **Сделать:** проверка `isFromServerPage` во всех обработчиках; `will-redirect` и `will-frame-navigate` только на свой адрес; явный `sandbox: true` и `app.enableSandbox()`; удалить `showToastNotification`, `toast.html` и их обработчики; журнал клиента в `app.getPath('logs')` без секретов.
- **Файлы:** `desktop/src/main/main.js`, `desktop/src/main/preload*.js`, `desktop/src/main/toast.html`.
- **Оценка:** 0,5 дня.

### 2.8. Защита сборки
- **Проблема:** не включены Electron Fuses; не проверяется целостность `app.asar`; cookie не шифруются; внутренний `OpenMyChat Enterprise.exe` не подписан.
- **Сделать:** в конфигурации electron-builder включить Fuses: выключить `RunAsNode`, `EnableNodeOptionsEnvironmentVariable`, `EnableNodeCliInspectArguments`; включить `EnableEmbeddedAsarIntegrityValidation`, `OnlyLoadAppFromAsar`, `EnableCookieEncryption`. Подписывать внутренний exe и DLL. Обновить Electron до актуальной версии ветки 44.
- **Файлы:** `desktop/package.json`, `desktop/scripts/sign-and-publish.ps1`.
- **Проверка:** чтение Fuses из собранного exe; подпись всех исполняемых файлов в `win-unpacked`; изменённый `app.asar` не запускается.
- **Оценка:** 1 день.

## Этап 3. Данные и журналы (недели 2–4, выкладка сервера)

### 3.1. Журнал аудита
- **Проблема:** не записываются: поиск администратора по всем перепискам, просмотр таблиц в консоли, неудачные входы, выдача токена по устройству, изменения ролей, зон и настроек, удаление каналов, скачивания файлов. Запись в журнал не ждёт результата. Имя пользователя попадает в консоль без очистки.
- **Сделать:** события для всех перечисленных действий (кто, что, сколько строк, IP); запись с ожиданием результата для действий администратора; очистка управляющих символов в строках журнала; журнал только на добавление.
- **Оценка:** 1,5 дня.

### 3.2. Чтение переписки администратором
- **Проблема:** поиск по всем сообщениям, включая личные, без ограничений и следа.
- **Решение:** читать переписку может только главный администратор (не администратор отдела); каждое чтение — событие в журнале аудита: кто, что искал, сколько строк.
- **Сделать:** проверка главного администратора на поиске по переписке и просмотре таблиц консоли; запись в журнал с ожиданием результата.
- **Оценка:** 0,5 дня.

### 3.3. Хранение
- **Решение:** переписка, файлы и журналы хранятся бессрочно; очистка не делается.
- **Следствие:** объём данных растёт — надёжность хранения и резервных копий (0.1, 3.4, 4.1) становится обязательной.

### 3.4. Шифрование и резервные копии
- **Проблема:** база и файлы не зашифрованы; резервные копии на том же диске, не включают вложения и базу учётных записей; API отдаёт полный путь к копии.
- **Сделать:** шифрование диска у провайдера или SQLCipher; зашифрованные копии (age или GPG) в отдельное хранилище вне Railway; копии включают вложения; для Postgres — резервирование провайдера или `pg_dump`; не отдавать абсолютный путь; проверка восстановления раз в квартал.
- **Оценка:** 1,5 дня.

### 3.5. Заголовки и токены
- **Проблема:** нет HSTS и CSP; токен на 7 дней, без выхода с отзывом, срок в миллисекундах, без `iat`/`iss`/`aud`; токен в `localStorage`; JSON до 5 МБ разбирается до проверки входа; тексты ошибок уходят в ответ.
- **Сделать:**
  1. HSTS; CSP для интерфейса: `script-src 'self'`, `object-src 'none'`, `connect-src 'self' wss:`.
  2. Короткий токен доступа и продление; `POST /auth/logout` с увеличением версии токена; поля `iat`, `iss`, `aud`; срок в секундах.
  3. Проверка длины `JWT_SECRET` при старте.
  4. Лимит JSON по маршрутам; общий текст ошибок в ответах 500.
  5. Токен в клиенте — через `safeStorage` главного процесса вместо `localStorage`.
  6. Проверка `Origin` при подключении WebSocket.
- **Оценка:** 2 дня.

### 3.6. Мелкие утечки
- **Проблема:** администраторы отделов получают рассылки устройств и заявок всей компании; список каналов отдаёт последний текст публичных каналов, где сотрудник не состоит; список пользователей показывает всем ожидающие и отклонённые заявки; `/health` отдаёт версию и тип хранилища.
- **Сделать:** фильтрация по зоне и участию; `/health` без подробностей для анонимных запросов.
- **Оценка:** 0,5 дня.

## Порядок работ и зависимости

1. Этап 0 — до любых изменений кода: без постоянного диска исправления сервера теряют смысл при следующем перезапуске.
2. 1.1–1.4 — первыми из кода: это вход без пароля, захват администратора и неотзываемые сессии.
3. 2.1–2.3 — одним выпуском клиента: все три касаются доверия к странице с сервера.
4. 2.4 делится: серверная часть выходит вместе с этапом 1, клиентская — с выпуском клиента.
5. 3.5 (токен в `safeStorage`) — вместе с выпуском клиента из этапа 2.
6. 4.1 и 3.3–3.4 проектировать вместе: перенос хостинга, хранение в Postgres, сроки хранения и копии.

## Критерии завершения

- Все задачи этапов 0–3 закрыты, у каждой есть автотест, воспроизводящий атаку.
- Повторный аудит по тем же направлениям не находит проблем высокой и критической опасности.
- `npm audit` — 0 уязвимостей высокого и критического уровня в сервере и клиенте.
- Восстановление из резервной копии проверено на отдельном стенде.
