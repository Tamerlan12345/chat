# Выпуск «безопасность и автообновление», октябрь 2026 — заметки для администратора

Что меняется для компании при выкладке этого выпуска, что нужно сделать один
раз при развёртывании и на что рассчитывать по железу. Про сам механизм
автообновления — отдельно, `docs/автообновление.md`; здесь — только сводка
того, что касается администратора и следует прочитать перед выкладкой.

## 1. Однократные последствия развёртывания

**Секрет каждого устройства станет недействительным.** Формат и правила
проверки входа по устройству («вход без пароля» на уже привязанном рабочем
компьютере) изменились в этом выпуске. После выкладки каждый сотрудник на уже
привязанном компьютере при следующем запуске приложения увидит обычный экран
входа и один раз введёт пароль — дальше устройство снова запомнит вход, как и
раньше. Это ожидаемо, предупредите сотрудников заранее, чтобы «опять просит
пароль» не превратилось в поток обращений в поддержку.

**Токены прежнего (миллисекундного) формата перестанут приниматься после
`LEGACY_TOKEN_CUTOFF` (по умолчанию 2026-10-15T00:00:00Z).** Если у кого-то
сохранилась очень старая копия клиента, после этой даты она потребует
обычного входа по паролю. Это не связано с выкладкой самого выпуска — отсечка
считается по времени, а не по факту обновления сервера.

## 2. Новые переменные окружения

Все — необязательные, со значениями по умолчанию, годными для обычной
установки. Добавлены в `.env.example` (см. там актуальные комментарии):

| Переменная | По умолчанию | Что делает |
|---|---|---|
| `DEVICE_SECRET_TTL_DAYS` | `30` | Через сколько дней «вход без пароля» на устройстве перестаёт работать сам по себе, даже если сотрудник не выходил из системы. См. ниже про связь с `SESSION_MAX_DAYS`. |
| `SESSION_MAX_DAYS` | `30` | Уже существовавшая переменная (не новая в этом выпуске) — максимальная длительность сессии без повторного подтверждения себя паролём. Упомянута здесь из-за связи с `DEVICE_SECRET_TTL_DAYS` ниже. |
| `LEGACY_TOKEN_CUTOFF` | `2026-10-15T00:00:00Z` | Дата, после которой токены прежнего (миллисекундного) формата перестают приниматься, даже если их срок ещё не истёк. Нераспознаваемое значение сервер игнорирует и пишет предупреждение в журнал — откатывается к дате по умолчанию, а не отключает проверку. |
| `IDENTITY_AUTO_IMPORT` | выключено | Осознанное разрешение перенести учётные записи из резервного файла (`data/identity.db`, `data/pre-identity-split.db`) в пустое хранилище. Без него сервер это делает не станет, даже если такой файл лежит на диске, — см. `docs/identity-store.md`. |
| `UPDATES_DIR`, `UPDATES_DISABLED`, `UPDATES_MAX_CONCURRENT_DOWNLOADS`, `UPDATES_MAX_FILE_MB` | см. `.env.example` | Автообновление настольного клиента. Подробности и остальные настройки (политика версий, каналы) — `docs/автообновление.md`; здесь не дублируются. |

### `DEVICE_SECRET_TTL_DAYS` и `SESSION_MAX_DAYS` — как они соотносятся

Это два независимых предела, и оба применяются одновременно:

- `DEVICE_SECRET_TTL_DAYS` — срок жизни самого секрета устройства (когда он
  становится недействительным и потребует обычного входа по паролю).
- `SESSION_MAX_DAYS` — как долго действителен сам токен без повторного
  подтверждения личности, отсчитывая от момента, когда сотрудник последний
  раз действительно вводил пароль (в том числе через claim секрета
  устройства).

Если `SESSION_MAX_DAYS` задан короче, чем `DEVICE_SECRET_TTL_DAYS`, — это
штатная, поддерживаемая комбинация: сервер сам сверяет оба предела при входе
по устройству, и как только заявка старше `SESSION_MAX_DAYS`, устройство
попросит войти по паролю заново, а не выдаст токен, который тут же будет
отклонён следующим запросом. Явно настраивать `DEVICE_SECRET_TTL_DAYS` под
`SESSION_MAX_DAYS` не обязательно, но если оба заданы вручную, разумно
ориентироваться на них как на связанные величины, а не выбирать независимо.

## 3. Стоимость хэширования пароля — ресурсы контейнера

Хэш пароля считается алгоритмом scrypt с параметром `N=2^17` (131072). Это
примерно 128 МиБ памяти на один расчёт (вход, смена пароля, первое
преобразование пароля из старого формата). Сервер допускает несколько
одновременных расчётов — при четырёх параллельных входах пиковое
дополнительное потребление памяти процессом может доходить примерно до
512 МиБ сверх обычного. При планировании памяти контейнера/сервера это стоит
учитывать отдельной строкой, особенно на утреннем всплеске входов всего
офиса разом.

## 4. Фильтр типов вложений — включён по умолчанию

Начиная с этого выпуска фильтр типов файлов на загрузку **включён по
умолчанию** и разрешает только заранее известный список расширений:

```
pdf, doc, docx, xls, xlsx, ppt, pptx, txt, csv, rtf, odt, ods,
png, jpg, jpeg, gif, webp, bmp,
zip, 7z, rar,
mp3, wav, ogg, m4a, mp4, webm, mov,
eml, msg, xml, json
```

Загрузка файла другого типа (например, `.sig`, `.p7s`, `.dwg`, `.tif`,
`.heic`, `.html`, `.log` и любого другого не из списка) отвечает HTTP 415 —
«Файлы .xxx к отправке не разрешены». Это не баг и не временная неполадка:
администратор (суперадминистратор) добавляет нужное расширение либо во весь
список сразу, либо только конкретному сотруднику (исключение) — во вкладке
**«Файлы»** консоли управления. Если сотрудники начнут жаловаться на «не
загружается файл» сразу после выкладки — в первую очередь проверьте, не
попадает ли их формат в список выше.

## 5. Сотрудники больше не редактируют своё ФИО и должность

Самостоятельное изменение профиля (`PUT /api/users/profile`) больше не
принимает ФИО и должность — эти поля показываются в каждом сообщении, в
оргструктуре компании и в справочнике сотрудников, и раньше их произвольная
смена самим сотрудником была способом выдать себя за кого-то ещё (например,
за «Службу поддержки» или руководителя, для фишинга внутри компании). Менять
их может только администратор (`PUT /admin/users/:id`). Email, телефон, фото
профиля и статус сотрудник по-прежнему меняет сам.

## 6. `GET /health` анонимному запросу отдаёт только статус

Без токена (или с токеном не суперадминистратора) ответ — `{"status": "ok"}`
и ничего больше: ни версии сервера, ни типа хранилища учётных записей, ни
времени работы. Раньше эти сведения были видны кому угодно, кто знает адрес
сервера, — полезная подсказка для подготовки атаки под конкретную версию.
Полный ответ (версия, хранилище, аптайм) по-прежнему доступен с токеном
суперадминистратора — для мониторинга и диагностики это тот же вызов, что и
раньше, только с заголовком `Authorization`.

## 7. Окна правки и удаления сообщений — по умолчанию 60 минут

Если раньше эти настройки не задавались явно, по умолчанию сотрудник может
править или удалять своё сообщение в течение 60 минут после отправки — оба
предела настраиваются отдельно в консоли администратора (это тот же
интерфейс, что и в предыдущих выпусках, значения по умолчанию явно
зафиксированы этим выпуском).

## 8. Мессенджер называется CentyChat

С этого выпуска (клиент 1.1.0) приложение называется **CentyChat** вместо
«OpenMyChat Enterprise»: окно, трей, уведомления, ярлыки, установщик
(`CentyChat-Setup-<версия>.exe`) и запись в «Установке и удалении программ».
Отдельных действий переименование не требует — это та же разовая установка
поверх 1.0.0, что и для автообновления. Данные сотрудников (вход, привязка
устройства, настройки) остаются на месте, повторно входить из-за
переименования не нужно.

Предупредите сотрудников о двух заметных мелочах: ярлыки теперь называются
«CentyChat», а значок, закреплённый на панели задач, после установки
пропадает — его нужно закрепить заново.

Ключ политики машины, который появился в этом выпуске, называется
`HKLM\SOFTWARE\Policies\CentyChat` — его и указывайте в групповой политике.
Имя сервера по умолчанию теперь «CentyChat Server», но у уже работающего
сервера оно хранится в базе: при необходимости поменяйте его в консоли
администратора (поле «Имя сервера мессенджера»).

Подробно — что меняется, что намеренно сохранило прежнее имя и куда
установщик кладёт новую версию — `docs/автообновление.md`, раздел 8.
