# Выпуск «безопасность и автообновление», октябрь 2026 — заметки для администратора

Что меняется для компании при выкладке этого выпуска, что нужно сделать один
раз при развёртывании и на что рассчитывать по железу. Про сам механизм
автообновления — отдельно, `docs/автообновление.md`; здесь — только сводка
того, что касается администратора и следует прочитать перед выкладкой.

## 1. Однократные последствия развёртывания

**Секрет каждого устройства станет недействительным.** Формат и правила
проверки входа по устройству («вход без пароля» на уже привязанном рабочем
компьютере) изменились в этом выпуске. После выкладки каждый сотрудник на уже
привязанном компьютере при следующем запуске приложения увидит обычный экран
входа и один раз введёт пароль — дальше устройство снова запомнит вход, как и
раньше. Это ожидаемо, предупредите сотрудников заранее, чтобы «опять просит
пароль» не превратилось в поток обращений в поддержку.

**Токены прежнего (миллисекундного) формата перестанут приниматься после
`LEGACY_TOKEN_CUTOFF` (по умолчанию 2026-10-15T00:00:00Z).** Если у кого-то
сохранилась очень старая копия клиента, после этой даты она потребует
обычного входа по паролю. Это не связано с выкладкой самого выпуска — отсечка
считается по времени, а не по факту обновления сервера.

## 2. Новые переменные окружения

Все — необязательные, со значениями по умолчанию, годными для обычной
установки. Добавлены в `.env.example` (см. там актуальные комментарии):

| Переменная | По умолчанию | Что делает |
|---|---|---|
| `DEVICE_SECRET_TTL_DAYS` | `30` | Через сколько дней «вход без пароля» на устройстве перестаёт работать сам по себе, даже если сотрудник не выходил из системы. См. ниже про связь с `SESSION_MAX_DAYS`. |
| `SESSION_MAX_DAYS` | `30` | Уже существовавшая переменная (не новая в этом выпуске) — максимальная длительность сессии без повторного подтверждения себя паролём. Упомянута здесь из-за связи с `DEVICE_SECRET_TTL_DAYS` ниже. |
| `LEGACY_TOKEN_CUTOFF` | `2026-10-15T00:00:00Z` | Дата, после которой токены прежнего (миллисекундного) формата перестают приниматься, даже если их срок ещё не истёк. Нераспознаваемое значение сервер игнорирует и пишет предупреждение в журнал — откатывается к дате по умолчанию, а не отключает проверку. |
| `IDENTITY_AUTO_IMPORT` | выключено | Осознанное разрешение перенести учётные записи из резервного файла (`data/identity.db`, `data/pre-identity-split.db`) в пустое хранилище. Без него сервер это делает не станет, даже если такой файл лежит на диске, — см. `docs/identity-store.md`. |
| `UPDATES_DIR`, `UPDATES_DISABLED`, `UPDATES_MAX_CONCURRENT_DOWNLOADS`, `UPDATES_MAX_FILE_MB` | см. `.env.example` | Автообновление настольного клиента. Подробности и остальные настройки (политика версий, каналы) — `docs/автообновление.md`; здесь не дублируются. |
| `LOGIN_ACCOUNT_SOFT_LIMIT` | `20` | Сколько неудачных входов в одну учётную запись со всех адресов вместе (за `LOGIN_LOCKOUT_MINUTES`) допускается, прежде чем включится задержка по этой учётной записи. См. раздел 8. |
| `LOGIN_ACCOUNT_MAX_DELAY_SECONDS` | `60` | Потолок этой задержки: сколько, в худшем случае, ждёт между попытками сотрудник с незнакомого адреса, пока к его учётной записи идёт подбор. |
| `LOGIN_ACCOUNT_UNFAMILIAR_PER_HOUR` | `30` | Пополнение общего «ведра» попыток с незнакомых адресов на одну учётную запись (ёмкость 10). Задаёт верхнюю границу подбора одной учётной записи со скольких угодно адресов — около 750 догадок в сутки. `0` — ведро выключено. См. раздел 8. |
| `PASSWORD_HASH_CONCURRENCY` | `2` | Сколько паролей сервер хэширует одновременно (каждый расчёт — около 128 МиБ). Остальные ждут в короткой очереди; переполненная очередь — ответ «сервер занят, повторите» (503). См. раздел 3. |
| `ANON_RATE_LIMIT_PER_MINUTE` | `12000` | Сколько запросов к API без входа принимается с одного адреса в минуту. Дешёвые публичные ответы (сведения о сервере, `/health`) под него не попадают. `0` — выключено; иначе не меньше 600. |
| `LOGIN_INFLIGHT_PER_IP` / `LOGIN_INFLIGHT_UNFAMILIAR` | `20` / `3` | Сколько проверок пароля с одного адреса идут одновременно: щедро для адреса офиса (знакомого хотя бы одному сотруднику) и жёстко мало для адреса, незнакомого никому. Сверх — 503, приложение повторит. Так один источник не занимает всю очередь проверок. |
| `UPLOAD_MAX_MB_PER_HOUR` | `2048` | Сколько мегабайт вложений один сотрудник может загрузить за час. `0` — без предела. |
| `UPLOAD_MIN_FREE_DISK_MB` | `1024` | Ниже этого запаса свободного места на диске загрузка файла отклоняется (507), чтобы не переполнить том и не оборвать запись базы. `0` — проверку выключить. |
| `WS_MAX_SOCKETS_PER_IP` | `2000` | Сколько одновременных соединений приложения допускается с одного адреса. Поднято с 500 под крупный офис за одним NAT. |
| `UPDATES_MAX_REQ_PER_MIN_PER_IP` | `6000` | Высокий потолок запросов автообновления с одного адреса. У каждой установки, кроме того, свой предел 120/мин по её идентификатору. |

`LOGIN_MAX_FAILED_ATTEMPTS` и `LOGIN_LOCKOUT_MINUTES` существовали и раньше, но
теперь проверяются: нечисловое, нулевое или отрицательное значение заменяется
значением по умолчанию (10 и 15) с предупреждением в журнале сервера. Раньше
опечатка в них молча выключала блокировку входа. То же правило действует для
всех новых переменных выше. `LOGIN_ACCOUNT_SOFT_LIMIT` должен быть больше
`LOGIN_MAX_FAILED_ATTEMPTS` — иначе оба откатываются к умолчанию.

Знакомые адреса входа хранятся в новой таблице `trusted_login_sources` (она
создаётся сама при первом запуске; отдельных действий не требует).

### `DEVICE_SECRET_TTL_DAYS` и `SESSION_MAX_DAYS` — как они соотносятся

Это два независимых предела, и оба применяются одновременно:

- `DEVICE_SECRET_TTL_DAYS` — срок жизни самого секрета устройства (когда он
  становится недействительным и потребует обычного входа по паролю).
- `SESSION_MAX_DAYS` — как долго действителен сам токен без повторного
  подтверждения личности, отсчитывая от момента, когда сотрудник последний
  раз действительно вводил пароль (в том числе через claim секрета
  устройства).

Если `SESSION_MAX_DAYS` задан короче, чем `DEVICE_SECRET_TTL_DAYS`, — это
штатная, поддерживаемая комбинация: сервер сам сверяет оба предела при входе
по устройству, и как только заявка старше `SESSION_MAX_DAYS`, устройство
попросит войти по паролю заново, а не выдаст токен, который тут же будет
отклонён следующим запросом. Явно настраивать `DEVICE_SECRET_TTL_DAYS` под
`SESSION_MAX_DAYS` не обязательно, но если оба заданы вручную, разумно
ориентироваться на них как на связанные величины, а не выбирать независимо.

## 3. Стоимость хэширования пароля — ресурсы контейнера

Хэш пароля считается алгоритмом scrypt с параметром `N=2^17` (131072). Это
примерно 128 МиБ памяти на один расчёт (вход, смена пароля, первое
преобразование пароля из старого формата). Одновременно идёт не больше
`PASSWORD_HASH_CONCURRENCY` расчётов (по умолчанию 2), поэтому пиковое
дополнительное потребление памяти на хэширование — около 256 МиБ сверх
обычного (раньше — до 512 МиБ). Остальные входы ждут в короткой очереди:
на утреннем всплеске это добавляет доли секунды на человека. Если очередь
переполнена (сотня ожидающих — так выглядит скорее подбор, чем утро), вход
отвечает «Сервер занят проверкой паролей — повторите через несколько секунд».
На сервере с запасом памяти значение можно поднять до 4; меньше 2 ставить не
стоит.

## 4. Фильтр типов вложений — включён по умолчанию

Начиная с этого выпуска фильтр типов файлов на загрузку **включён по
умолчанию** и разрешает только заранее известный список расширений:

```
pdf, doc, docx, xls, xlsx, ppt, pptx, txt, csv, rtf, odt, ods,
png, jpg, jpeg, gif, webp, bmp,
zip, 7z, rar,
mp3, wav, ogg, m4a, mp4, webm, mov,
eml, msg, xml, json
```

Загрузка файла другого типа (например, `.sig`, `.p7s`, `.dwg`, `.tif`,
`.heic`, `.html`, `.log` и любого другого не из списка) отвечает HTTP 415 —
«Файлы .xxx к отправке не разрешены». Это не баг и не временная неполадка:
администратор (суперадминистратор) добавляет нужное расширение либо во весь
список сразу, либо только конкретному сотруднику (исключение) — во вкладке
**«Файлы»** консоли управления. Если сотрудники начнут жаловаться на «не
загружается файл» сразу после выкладки — в первую очередь проверьте, не
попадает ли их формат в список выше.

## 5. Сотрудники больше не редактируют своё ФИО и должность

Самостоятельное изменение профиля (`PUT /api/users/profile`) больше не
принимает ФИО и должность — эти поля показываются в каждом сообщении, в
оргструктуре компании и в справочнике сотрудников, и раньше их произвольная
смена самим сотрудником была способом выдать себя за кого-то ещё (например,
за «Службу поддержки» или руководителя, для фишинга внутри компании). Менять
их может только администратор (`PUT /admin/users/:id`). Email, телефон, фото
профиля и статус сотрудник по-прежнему меняет сам.

## 6. `GET /health` анонимному запросу отдаёт только статус

Без токена (или с токеном не суперадминистратора) ответ — `{"status": "ok"}`
и ничего больше: ни версии сервера, ни типа хранилища учётных записей, ни
времени работы. Раньше эти сведения были видны кому угодно, кто знает адрес
сервера, — полезная подсказка для подготовки атаки под конкретную версию.
Полный ответ (версия, хранилище, аптайм) по-прежнему доступен с токеном
суперадминистратора — для мониторинга и диагностики это тот же вызов, что и
раньше, только с заголовком `Authorization`.

## 7. Окна правки и удаления сообщений — по умолчанию 60 минут

Если раньше эти настройки не задавались явно, по умолчанию сотрудник может
править или удалять своё сообщение в течение 60 минут после отправки — оба
предела настраиваются отдельно в консоли администратора (это тот же
интерфейс, что и в предыдущих выпусках, значения по умолчанию явно
зафиксированы этим выпуском).

## 8. Защита от подбора пароля — что изменилось для сотрудников

Подробности и обоснование — `docs/superpowers/specs/2026-09-29-security-audit-round4.md`.

**Задержка по учётной записи.** Раньше пределы входа считались только по
адресу, и подбор пароля к одной учётной записи с многих адресов ничем не
ограничивался. Теперь, если к одному логину со всех адресов вместе накопилось
больше `LOGIN_ACCOUNT_SOFT_LIMIT` (20) неудачных попыток, попытки с
**незнакомых** адресов допускаются по одной и с растущей паузой — до
`LOGIN_ACCOUNT_MAX_DELAY_SECONDS` (60 с). Сотрудник видит «Слишком много
неудачных попыток входа под этим логином. Повторите через N с.».

- **Сотрудника это не запирает.** С адреса, откуда он уже проходил проверку
  личности (вход по паролю, «вход без пароля» на привязанном ПК, обычная
  работа приложения), задержки нет вовсе, сколько бы попыток ни шло извне.
  Этот список знакомых адресов теперь переживает перезапуск сервера.
- **С нового для себя адреса** (впервые из дома, с мобильного интернета) под
  идущей атакой попытки с незнакомых адресов черпают из общего для учётной
  записи «ведра» (ёмкость 10, пополнение `LOGIN_ACCOUNT_UNFAMILIAR_PER_HOUR` в
  час). Пока в ведре есть попытки — первый заход с нового адреса проходит
  сразу; когда атакующий вычерпал ведро, сотрудник с нового места видит
  «Войдите с рабочего компьютера или обратитесь к администратору» и ждёт
  (попытка возвращается в ведро примерно раз в две минуты). **Это честная
  цена:** под активным подбором ИМЕННО его учётной записи вход с совершенно
  нового места может быть отложен. Твёрдо гарантирован вход с **знакомого**
  адреса и с **привязанного устройства** — они не ограничены ничем из этого.
- **Верхняя граница подбора одной учётной записи** со скольких угодно адресов —
  около 750 догадок в сутки (было ≈960 на КАЖДЫЙ адрес). Навсегда запереть
  учётную запись нельзя — ни извне, ни изнутри.
- **Восстановление.** Сброс пароля этого сотрудника администратором сразу
  снимает всю задержку с его учётной записи — он снова входит откуда угодно.
- **Привязанные устройства** («вход без пароля») этой защите не подчиняются
  вовсе.
- **Один ошибающийся сотрудник её не вызывает:** со своего адреса он упрётся
  сперва в прежнюю блокировку «адрес + логин» (10 попыток, 15 минут), а
  защита по учётной записи включается только от неудач с нескольких адресов.
- **Чего защита не делает сама:** предел неудач на сеть /64 и оповещение
  «Подбор пароля к одной учётной записи с нескольких адресов» в центре
  безопасности дополняют её, а в пределе — список разрешённых адресов
  `ALLOWED_CLIENT_IPS`.

**Утренний вход всего офиса за одним NAT не запирает сам себя.** Верные входы
предел неудач не расходуют вовсе. Если сотни человек входят в одну секунду,
часть запросов может получить «Сервер сейчас обрабатывает много входов,
повторите через несколько секунд» (503) — приложение повторит само; это не
блокировка. Пределы одновременных соединений и запросов обновлений подняты под
крупный офис.

**Смена пароля.** Неверный текущий пароль при смене — не больше 5 раз за 15
минут (`LOGIN_LOCKOUT_MINUTES`) на самого сотрудника. Саму смену пароля
задержка входа (которую мог бы раскрутить посторонний, засыпая чужой логин)
теперь НЕ блокирует: у сотрудника действующий вход, и сменить пароль он может
всегда.

**Адреса IPv6.** Все пределы по адресу теперь считаются по сети /64: так
провайдеры выдают адреса одному абоненту. Офис за IPv6 ведёт себя ровно как
офис за одним IPv4 NAT.

**Прочие пределы.** Поиск по переписке — не больше 30 запросов в минуту и
строка до 200 символов; загрузки вложений — `UPLOAD_MAX_MB_PER_HOUR` (2 ГБ в
час на сотрудника); не больше 200 заявок на регистрацию, ожидающих решения
администратора.

## 9. Новые правила пароля — только для нового пароля

При **задании и смене** пароля (сотрудником, администратором, при создании
учётной записи, регистрации, импорте, а также для `INITIAL_ADMIN_PASSWORD` и
`ADMIN_PASSWORD_RESET`) теперь отклоняются:

- распространённые пароли (`password1`, `1q2w3e4r`, `qwerty123`, `йцукен123`
  и т. п.) и «время года + год» (`Лето2026`);
- название компании и продукта во всех видах — латиницей, кириллицей, в наборе
  не в той раскладке — с любыми цифрами, знаками и разделителями: `Centychat1`,
  `Centras@2026`, `centy.chat1`, `сентичат123`, `ctynhfc123`, `mychat2026` и
  подобные (включая подмену похожими латинскими буквами, `Lето2026`);
- пароль, равный логину, логину задом наперёд или логину с цифрами и знаками
  в конце (`ivanov2026!` для логина `ivanov`);
- пароль из одного-двух повторяющихся символов;
- как и раньше — короче 8 символов.

**Действующие пароли продолжают работать.** При входе новые правила не
применяются: сотрудник, чей пароль под них не подходит, входит как обычно и
без требования сменить пароль (прежнее требование сменить пароль вроде
`123456` при входе осталось как было). Новые правила он встретит только при
следующей смене пароля. (На будущее возможно, но пока не включено, требование
сменить и такие пароли — из списка распространённых и марочных — при первом
входе после выкладки; сейчас это не делается, чтобы не поднять волну смен.)

**Внимание при развёртывании с нуля:** если `INITIAL_ADMIN_PASSWORD` окажется
в списке распространённых или равен `admin` с цифрами, сервер на **пустой**
базе не стартует и назовёт причину — задайте другой. На уже заполненной базе
эта переменная не используется. `ADMIN_PASSWORD_RESET` с таким значением не
применяется (предупреждение в журнале), пароль остаётся прежним.

## 10. Мессенджер называется CentyChat

С этого выпуска (клиент 1.1.0) приложение называется **CentyChat** вместо
«OpenMyChat Enterprise»: окно, трей, уведомления, ярлыки, установщик
(`CentyChat-Setup-<версия>.exe`) и запись в «Установке и удалении программ».
Отдельных действий переименование не требует — это та же разовая установка
поверх 1.0.0, что и для автообновления. Данные сотрудников (вход, привязка
устройства, настройки) остаются на месте, повторно входить из-за
переименования не нужно.

Предупредите сотрудников о двух заметных мелочах: ярлыки теперь называются
«CentyChat», а значок, закреплённый на панели задач, после установки
пропадает — его нужно закрепить заново.

Ключ политики машины, который появился в этом выпуске, называется
`HKLM\SOFTWARE\Policies\CentyChat` — его и указывайте в групповой политике.
Имя сервера по умолчанию теперь «CentyChat Server», но у уже работающего
сервера оно хранится в базе: при необходимости поменяйте его в консоли
администратора (поле «Имя сервера мессенджера»).

До выкладки: обновите правила AppLocker/SRP, брандмауэра и исключения
антивируса, привязанные к имени или пути `OpenMyChat Enterprise.exe`, и
прогоните переход с настоящей 1.0.0 на виртуальной машине (тихая установка,
обычная установка и установка «копией») — список проверок там же.

Подробно — что меняется, что намеренно сохранило прежнее имя, куда
установщик кладёт новую версию и как он убирает установку «копией» —
`docs/автообновление.md`, раздел 8.
