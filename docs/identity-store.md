# Хранилище учётных записей в PostgreSQL

## Что где лежит

| Данные | Где | Почему |
|---|---|---|
| Сотрудники, пароли, роли, подразделения, привязки устройств, журнал действий, настройки сервера | **PostgreSQL** | Требуют надёжного хранения, резервного копирования средствами СУБД и недостижимости из админ-панели |
| Сообщения, каналы, участники, объявления, отметки о прочтении, файлы | **SQLite** (`server/data/mychat.db`) | Переписка остаётся там, где была |

Переписка в PostgreSQL не хранится — это отдельное требование, а не следствие.

## Зачем разделять

В админ-панели есть студия базы данных: суперадминистратор выполняет
произвольный SQL и скачивает резервные копии одним нажатием. Пока учётные
записи лежали в том же файле, это означало, что хэши паролей всех сотрудников
достижимы прямо из веб-интерфейса — `SELECT password_hash, salt FROM users`, и
дальше подбор в спокойной обстановке.

После разделения студия работает только с базой переписки. Таблицы `users` там
больше нет вовсе, а `ATTACH DATABASE` запрещён отдельно — иначе на запасном
хранилище SQLite соседний файл можно было бы подключить к сессии.

## Как настроить

Достаточно одной переменной:

```
DATABASE_URL=postgresql://пользователь:пароль@узел:5432/база
```

Без неё сервер поднимется на запасном хранилище SQLite (`server/data/identity.db`)
и скажет об этом в журнале при каждом запуске. Это рассчитано на разработку и
автотесты, а не на рабочую установку.

### Railway

1. В проекте: **New → Database → PostgreSQL**.
2. В сервисе приложения, вкладка **Variables**, добавить ссылку на переменную
   базы: `DATABASE_URL = ${{Postgres.DATABASE_URL}}`. Railway подставит адрес
   внутренней сети (`postgres.railway.internal`), трафик наружу не выходит.
3. Задать `JWT_SECRET` — иначе при каждом развёртывании генерируется новый и
   все выданные токены перестают действовать.
4. **Удалить `ADMIN_PASSWORD_RESET`**, если она осталась: пока переменная на
   месте, пароль администратора известен каждому, у кого есть доступ к
   настройкам развёртывания.

### Docker Compose

`docker-compose.yml` поднимает PostgreSQL рядом. Перед первым запуском:

```bash
cp .env.example .env
# заполнить POSTGRES_PASSWORD и INITIAL_ADMIN_PASSWORD
docker compose up -d
```

Порт базы наружу не публикуется.

### TLS

По умолчанию: проверяемый TLS для внешних узлов, без TLS для локальных и
внутренних адресов (`localhost`, `*.railway.internal`, `10.*`, `192.168.*`,
`172.16–31.*`) — там трафик не покидает частную сеть, а сертификата у
внутреннего имени нет.

Ослабить проверку можно только явно, `DATABASE_SSL=no-verify`, и сервер будет
писать об этом предупреждение при каждом запуске. Свой корневой сертификат —
`DATABASE_CA_CERT`.

## Переход с прежней версии

Выполняется сам, при первом запуске с настроенным `DATABASE_URL`:

1. Если в новом хранилище нет ни одного сотрудника, а в базе переписки есть
   таблица `users` с записями — всё содержимое переносится **с сохранением
   идентификаторов**. На эти номера ссылаются сообщения, участники каналов и
   объявления; сдвиг хотя бы на единицу перемешал бы авторство переписки.
2. Подразделения переносятся в два прохода: сначала строки, потом связи с
   родителями. Иначе ссылка на ещё не вставленного родителя нарушила бы
   внешний ключ.
3. Счётчики идентификаторов PostgreSQL сдвигаются за наибольший занятый номер.
   SQLite делает это сам, PostgreSQL — нет, и без этого шага первая же новая
   запись столкнулась бы с существующей.
4. Рядом с базой переписки сохраняется снимок `data/pre-identity-split.db` —
   на случай отката. Он лежит **не** в каталоге резервных копий: тот отдаётся
   администратору по HTTP, а этот файл ещё содержит пароли.
5. Из базы переписки снимаются внешние ключи на `users` (таблица теперь в
   другой базе, проверить такую ссылку СУБД не может) и удаляются перенесённые
   таблицы.

Пароли переносятся как есть и продолжают работать. При первом успешном входе
каждый пересчитывается в новый формат — это единственный момент, когда сервер
знает пароль в открытом виде.

## Что изменилось в безопасности

**Хранение паролей.** Было: `scryptSync` с параметрами по умолчанию, соль в
соседней колонке, сравнение оператором `===`. Стало: `scrypt` с N=32768,
асинхронный (вход перестал останавливать обслуживание всех остальных),
параметры записаны рядом с ключом — поднять их позже можно, не ломая уже
сохранённые пароли. Сравнение — `crypto.timingSafeEqual`: по длительности
обычного сравнения строк ключ подбирается побайтно.

**Отзыв токенов.** У каждой учётной записи есть номер поколения. Он сдвигается
при смене пароля, смене роли, отключении сотрудника и отклонении заявки — и все
выданные раньше токены перестают приниматься немедленно, а не доживают свои семь
дней. Смена пароля, после которой чужая сессия продолжает работать, защищает
только на словах.

**Блокировка при подборе.** Счётчик неудачных попыток хранится в базе, а не в
памяти процесса: перезапуск сервера и смена адреса подбор больше не
возобновляют. После 10 попыток — 15 минут (настраивается).

**Пароли по умолчанию.** Было: каждая новая учётная запись получала «123456»,
и он же подставлялся при сбросе. Между заведением и первым входом сотрудника
это открытая дверь — войти, сменить пароль и занять чужую личность успевал
кто угодно. Стало: если администратор не задал пароль явно, сервер выдаёт
случайный и показывает его ровно один раз.

**Требования к паролю.** Не короче 8 символов, десяток общеизвестных запрещён.
Жёстче делать не стали: в корпоративной среде это переселяет пароль на бумажку
под клавиатурой.

**Справочник сотрудников.** `GET /api/users` больше не отдаёт `bound_ip`,
`admin_scope_dept_id` и состояние заявки: адрес рабочего места коллеги —
сведение служебное, а устройство прав доступа не должно читаться из справочника.

**Внедрение SQL.** Все запросы параметризованы. Единственное место, где
собирается список подстановок, — фильтры по набору идентификаторов, и туда
попадают только числа, прошедшие `Number`. Отдельный тест проверяет, что во
всех запросах к хранилищу используется нумерованная форма `$1` — позиционный
`?` работает в SQLite и молча ломается в PostgreSQL.

## Резервное копирование

Теперь копий две, и делаются они по-разному:

- **Переписка** — как и раньше: по расписанию в `server/data/backups`, плюс
  кнопка в админ-панели.
- **Учётные записи** — средствами PostgreSQL. На Railway включены
  автоматические копии базы. Для своей установки:
  `docker compose exec mychat-db pg_dump -U mychat mychat > identity.sql`

Выгрузка учётных записей содержит хэши паролей — хранить её надо как
чувствительные данные, а не в общей папке.

## Тесты

```bash
npm test               # весь набор на запасном хранилище SQLite
npm run test:pg        # тот же набор на настоящем PostgreSQL во временном контейнере
npm run test:identity  # только хранилище: пароли, диалект SQL, перенос
```

`npm run test:pg` обязателен перед выкладкой изменений, затрагивающих
хранилище. Часть ошибок видна только на PostgreSQL — так, несдвинутый счётчик
идентификаторов после переноса на SQLite не проявляется вовсе.
