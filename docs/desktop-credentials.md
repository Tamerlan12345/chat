# Desktop credential storage

The upgraded Electron shell stores session tokens and device identity in an OS-encrypted vault under the existing userData directory. Each configured server origin has a separate hashed filename. Electron safeStorage must report encryption available; the Linux basic_text backend is rejected. Writes use an exclusive temporary file, fsync and atomic rename. Encryption, read or write failure never switches an upgraded client to plaintext storage.

Only the configured server's top frame in the main window may call the five credential IPC methods. Main owns generation and use of the paired-device secret. Claim and knock have fixed endpoint paths on that configured origin, bounded requests and redirect rejection. Renderer input cannot select a destination or provide a replacement secret for these operations. The renderer still receives the active bearer token for HTTP/WebSocket operations, in memory; this change protects persistence and device-secret exposure, not an active session against server-origin XSS.

## Migration and compatibility

On the first launch of the upgraded shell with the updated renderer, legacy localStorage credentials are submitted once to main. The stored server origin must match the configured origin. The renderer deletes the token, device secret and device ID from localStorage only after main confirms encrypted persistence. An existing vault takes precedence over stale legacy values, including after logout. Migration is idempotent across a crash between persistence and removal. Legacy secrets necessarily already existed in renderer memory/storage; migration cannot revoke previously copied data or guarantee forensic erasure of Chromium files, backups, swap or disk history.

The renderer is delivered by the server, so an older installed shell has no credential IPC. Capability detection deliberately preserves its existing login, silent pairing, refresh and localStorage behavior until that shell is upgraded. Ordinary browser clients use the same legacy path. **Those clients still have the original plaintext-storage risk.** Deploying the renderer alone does not close the finding; release/install the upgraded shell, confirm migration on supported OS versions, then retire legacy compatibility according to deployment policy. A present-but-failing secure bridge never falls back to legacy behavior.

Changing the server for an upgraded shell uses the existing managed/native server configuration and a restart. A renderer-entered foreign server cannot receive the retained credentials. A legacy profile labelled with a different server fails migration explicitly; reconnect to that server through native configuration or intentionally clear that profile before pairing a new identity. The vault is bound to the OS account and server origin and is not a portable backup format.

## Session behavior and limits

Password login persists the returned token before opening a session and claims the device through main. Silent knock persists the reissued token in main. Refresh and password changes update the encrypted token and renderer memory. Admin components read the memory token. Logout retains the existing bounded server unbind and revoke requests (with the device ID), then clears the encrypted token and secret before reloading. The persisted logout flag suppresses silent login. If OS decryption becomes unavailable, logout can delete ciphertext without decrypting it. If the server cannot be reached during logout, server-side revocation remains best effort, as before; previously copied credentials may remain valid until server expiry/revocation.

Node tests cover IPC rejection, origin isolation, request destinations, migration acknowledgment, corrupt/unavailable storage, atomic-write failure, restore, token renewal, logout and legacy compatibility. Their encryption adapter is an authenticated-encryption test double, not a claim that Windows DPAPI or Linux keyrings were exercised. A real packaged Electron install, OS keyring lock/unlock, reboot and upgrade migration still need release smoke testing. Build success does not prove an installed-client rollout.
